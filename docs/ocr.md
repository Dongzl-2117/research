# 图片里的字（OCR）

截图里的财报表格、聊天记录、标注过的图表，检索和问库原来完全看不到。现在把本地图片（归档里带的、从外链下载来的，见 [ingest.md](ingest.md)）交给 RapidOCR 识别，识别出的字切成段落块进检索。

- 按图片内容哈希只识别一次，结果存在 `image_texts`。多篇引用同一张图不重复识别；识别不出字的也记一行，不反复去认。
- 置信度低于 0.5 的文字框不要（多半是花纹、二维码认成了字）。文字框按阅读顺序拼：从上到下分行，同一行从左到右。
- 识别出的汉字、字母、数字够 20 个的图才切检索块：`article_chunks.lang = 'ocr'`，块号从 20000 起，标题「图片里的字」，锚点是 `img-<哈希前 12 位>`。检索和问库走这些块，不另建索引。
- 阅读、摘要、观点放宽到 8 个字。空白、水印、几个字的装饰不算。刚过线的拿不准，算有用，不能漏。不按「是不是微信、是不是表格」分：有可读的字就用。
- 公司提及不看图片里的字，免得水印、表情包里的字乱记。这条不变。
- 识别结果另外写在文章旁路 `articles.ocr_text`。微信群聊截图先整理成「方伟：」「网友：」再写入：绿色气泡是作者自己，标成方伟；灰色、带别人昵称的标成网友，不留本名（含「徐哲航@think」、Dylan）。新识别从原图 RGB 采样气泡颜色，不按左右位置猜测。只有标准浅色或深色主题的绿色/中性灰色填充且可确认气泡边界时才写入颜色标记；颜色不明又无明确昵称时显示「未确认：」，不继承上一气泡的作者。历史侧标记仅兼容读取。没有原图的排序调用不生成颜色证据；不能仅因为文字靠右就认作方伟。旧侧标记只兼容读取，无法替代原图复核。显示名「方伟-最近在杭州」仍是方伟。句子里的 @方伟 不是说话人。方伟连续说的合成一块，网友每次开口仍分开。同一说话人的跨图重叠句子只留一次；网友和方伟重复同一句话时保留双方归属。群名、价格（含粘在商品上的「￥19.?」）、小程序及其误识「小小程序」、美团外卖、店名和商品卡、「设为群待办」、状态栏时间（含「10:38≥」）这些界面字去掉。知识星球的引用回复不是这套绿/灰气泡：第一条「方伟看十年」或「方伟看十年作者」账号栏上面的灰字是「网友：」，栏下的回复是「方伟：」，账号栏和下一帖标题去掉；栏上没有正文时仍整段是方伟。表格和贴成长文的图仍是原文。摘要和观点交给模型的正文接上这份整理后的字，和正文一视同仁。有效字少于 8 个的图不进这条旁路。打开文章只读取并临时整理现有识别，不回写旁路、不排队。明确的 OCR / 摘要 / 观点处理命令才会写入允许处理的文章。观点和摘要再读这篇时，只要还挂着 `image_texts`，也会按当前规则从原始识别重写，避免库里已经写成「方伟：」的旧旁路把引用回复分不回来。
- 明确处理正文不足 400 字的文章时，图片文字和上次抽的时候不一致，摘要候选会重新计算；打开文章不会排队。已经写出判断的长文不会因为后补了一张图就整篇重抽。
- 观点队列：深入提及照旧。正文不足 400 字、图片里又有字的，一带而过也抽——判断经常在截图里，不能因为深度是一带而过、或内容来自截图就跳过。长文里顺带一提的公司，不会只因为旁边有张图就抽。夜间任务仍按原来的篇数上限，深入提及排在前面；全库重跑不由这次改动自动开始。单篇可以用 `research-views --articles <id>`。公司不在公司表里就没有观点可抽。
- 重复文章（见 [ingest.md](ingest.md)）里的图不认。身份未知、被排除的星球帖子和仅含星主回复的网友帖子，不使用原帖图片或历史 OCR。OCR 候选与执行入口同时核对身份和已验证正文投影；共享图片哈希不会让网友文章绕过这条规则。

## 颜色证据与定向复核

颜色标记存入 `image_texts.text`，呈现时去掉，不改模型配置或数据库结构。#55 已通过作者回复头修复 12681 的两条回复，并提供 606 / 12681 / 473 原始 OCR 片段回归。此后的新 OCR 另外采样气泡底色；只重洗旧文本不能补出颜色。如果要用颜色复核历史 12681，应在部署后对该文章的原图定向重新 OCR（现有 `research-ocr --redo --article 12681` 路径），再检查 present。本次只改代码，没有执行生产 OCR、回写、观点重提或全库任务。

颜色测试使用明确标注的合成 RGB 图，覆盖绿色/灰色、左右互换、不确定颜色、同一行两种气泡和正文保留。8881 使用已提交的真实 OCR；14884 的自动回归使用 #55 PR 中的输出片段。本轮另在 mini 本地查看了实际存在的原图，不将私有原图放入仓库。606 的暗色微信原图采样到绿色约 (41, 180, 97)、网友灰色约 (44, 44, 44)、背景约 (17, 17, 17)，修复前两类气泡均被视为未知，修复后能在有边界的区域识别。自动颜色测试仍使用明确标注的合成栅格。#55 的 473 原始商品卡片段和 12681 完整回复片段测试保留。支持范围之外的主题、截图裁边或颜色不清的区域不强行分配给作者。普通报告正文中出现「微信」或图表中的 Mobile / Tencent 标签，不再被单凭关键词、昵称形状套成方伟对话。保留多列空格以识别换行表格；商品卡、优惠券、图表不写成说话人的观点。

页脚沿用 #55 的整行规则（包括「观察 56个朋友关注 82 455 38 33。」整行删除）；新增处理计数另起一行及历史旁路给纯 UI 套过说话人标签的情况，不从第一个按钮截到末尾。`fangwei-zsxq` 和 `fangwei-mp` 继续共用 ingest / present / repair 清洗路径。

## 阅读页

文章页和飞书目录里的正文现查 `image_texts`，用和旁路同一套整理（`wechat_dialogue`）。群聊显示成「方伟：」「网友：」，连续几张截图合成一段，重复的句子不重复出现。原图不再每张叠一个「点击看原图」，而是收成一行「原图 1」「原图 2」，点开就是图片地址。表格、长文仍按原文换行，原图收在「点击看原图」里。字太少或还没识别的图保持现在的图片。整理完不够读就仍用识别原文，不编对话。新跑完的图刷新页面就能看见，不用重导正文。检索里的「看这张图」仍跳到 `img-<哈希前 12 位>`，落在对应的原图链接上。检索块本身仍是识别原文，方便按原句查找。

## 单独的镜像

RapidOCR 要 onnxruntime 和 OpenCV，装上以后镜像大很多，所以不进主镜像，另有一个 `ocr` 镜像（Dockerfile 里的 `ocr` 阶段，在应用镜像上加 RapidOCR，依赖按 `requirements-ocr.lock` 锁死）。模型文件在安装包里，跑的时候不联网下载。只用 CPU。

```bash
docker compose --profile ocr build ocr
docker compose --profile ocr run --rm ocr research-ocr --limit 500
docker compose --profile ocr run --rm ocr research-ocr --limit 5000 --max-minutes 120
# 存量已经在 image_texts 里的图，要重认时加 --redo（全库约 2 万张，部署后在 Mac mini 上跑，不要在云端对生产库跑）
docker compose --profile ocr run --rm ocr research-ocr --redo --limit 5000 --max-minutes 120
# 只认某几篇里的图
docker compose --profile ocr run --rm ocr research-ocr --article 7711 --article 7865 --article 7638 --article 7832 --article 651
```

主镜像里跑 `research-ocr` 会直接退出（退出码 2），提示改用 `ocr` 镜像。

OCR 写完后，图片帖的空白观点会因为 `ocr_hash` 对不上而进入补抽。确认「图片里的字进了观点输入」可以看这几篇（约 33 张图）：

```bash
docker compose exec app research-views --gap --articles 7711,7865,7638,7832,651
```

抽完后这几篇若原文在图里写了判断，`company_views.judgment` 不应再是空的，原句应能对上 `articles.ocr_text`。

说话人规则改了以后，已经写成非空判断的文章不会因为 `ocr_hash` 变化就自动重抽（正文短于 400 字、或判断仍是空白的才会）。文章 8881 的拼多多截图把栏上「不太看好」标成了方伟，要按这一篇重抽它提到的公司，不要全库、也不要加 `--gap`（`--gap` 会跳过已经有非空判断的）：

```bash
docker compose exec app research-views --articles 8881
```

阅读页本身现解析 `image_texts`，部署后打开即是「网友：」在账号栏上、「方伟：」在栏下，不必重跑 RapidOCR。上面这条命令会先按原始识别重写 `articles.ocr_text`，再重抽该篇的 `company_views`（拼多多，以及同一篇里从这张图写出的其他公司）。

知识星球和公众号截图上的页脚按行丢掉，不从第一行按钮截到图末。单独成行的按钮、粘在一行里的「分享21 推荐0 划线人数0」「赞赏￥0」「3条留言V 写留言」，以及公众号的「微信小店」「关注同城」「相关的服务号」，都不进「方伟：」。这些行后面的方伟、网友继续留着。「张冠留言」「张冠留言1次·关注8个月」，以及名字后粘着拉丁字母的「郑立涛ILetterZheng留言1次·关注3个月」「UI留言17次·新的关注」，改成网友的一轮（就算这一行已经写成「方伟：…留言头」）。「22:07上海」这种钟点加地名删掉。公众号再删「+关注」「14个朋友关注 3 19。」，账号名和按钮粘在一行的「饮料快暴 +关注」「品饮汇 品饮汇观察 +关注」，以及按钮后粘着阅读量的「观察 56个朋友关注 82 455 38 33。」也整行删；正文里提到「朋友关注」的句子不动。知识星球回复头的「方伟在学习（作者）2」是说话人分界，下面是方伟；「方伟看十年（作者）」仍是引用回复的账号栏。微信小店、拼多多、淘宝的商品卡截图不套对话，阅读页只留原图链接；正文句子里的「微信小店」照常保留。阅读页现解析，不必重跑 RapidOCR。部署后再跑一次回写，12681、473、606 的旁路会按新规则重洗（见 [ingest.md](ingest.md)）。`research-repair-zsxq` 同时重洗 `fangwei-zsxq` 和 `fangwei-mp`：

```bash
docker compose exec app research-repair-zsxq --dry-run
docker compose exec app research-repair-zsxq
docker compose exec app research-views --articles 203,227,473,537,606
```

不要加 `--gap`，也不要全库。8881 的拼多多已经抽过。抽验锚点是 12681、473、606。

## 每晚补一批

夜间任务（[backup.md](backup.md)）默认不跑 OCR。镜像建好以后：

```bash
NIGHTLY_OCR=1 BACKUP_DIR=… scripts/install-launchd.sh
```

之后每晚在观点、摘要、论点之后再识别一批（`OCR_LIMIT`，默认 400 张，和其他步骤共用 `MINUTES` 的时间上限），失败了和其他步骤一样记进夜间任务的结果，首页提示。

第一次可以先手动跑一大批把存量认完，以后每晚只剩新导入的图。

## CI

CI 会构建 `ocr` 镜像，用 `tests/fixtures/ocr-sample.png`（三行中文）跑一遍，认不出「拼多多」「广告收入」「货币化率」或行的顺序不对就失败。锁文件里的版本升级以后，靠这一步确认还能用。
