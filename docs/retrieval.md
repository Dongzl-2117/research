# 检索怎么找原文

检索页（`/search`）、问库（`/ask`）和 JSON 接口（`/api/v1/search`、MCP 的 `search_library`）用的是同一套召回和打分，代码在 `src/researchlib/retrieval.py`。目标是两件事：针对问的问题，找出相关性最高的原文段落；库变到几十万段以后，仍然准、全、快。

## 当前修复的边界与验证

召回、排序、相邻上下文、模型整合、引用回链仍是一条通用链路，没有为某家公司或某个主题加固定关键词答案，也没有新增一次模型重排调用。查询中的新说法即使在词频中为零，也保留主题意图，让已有向量通道参与。指定公司时不再开放一条不限公司的向量召回；公司证据来自当前投影相符的提及记录，或已核实原文片段中的公司别名。仅顺带提及公司的段落会在融合后降权。

向量必须仍对应当前块、当前配置的向量模型和当前标题/章节/正文哈希。旧星球原帖可以复用能由可信账户原文投影逐段证明的正文块；未知身份、被移除评论、旧 OCR、旧译文不能借这个例外进入模型上下文。历史摘要、公司观点和公司提及采用更严格的完整投影一致性要求；因此它们的可用篇数可能少于已确认作者的原帖数，需要后续显式导入/处理才能恢复。网页读取不会自动补算。

检索来源分面和「词条完整命中」使用同一组文章 ID，覆盖正文、合规 OCR、当前译文以及散落在不同块的词组，并应用同一范围、去重和排除词条件。语义相关另计，和词条完整命中按融合相关性排列，不伪装成字面命中。精确命中的文章即使不在有限的初始候选池里，后续页仍有结果；语义相关和部分命中只代表有限候选池，不代表穷尽语义召回。

新回答在整合前保存全部模型输入文章的不可变来源凭据，包括未被最终引用的材料和目录标题；整合后再次比较，期间原文或身份变化就不发布。读取历史回答时重新核对完整凭据，缺少旧输入凭据的记录不会因为文章后来重新导入而恢复展示，也不会自动重新整合。

本次离线单元测试验证的是账户/范围边界、陈旧向量拒绝、通用实体约束、非字面机制排序、分面与分页、上下文隔离及引用编号。人工对实际库的段落检查只算段落阅读，不算全文阅读或原图对照；文档下方旧版合成语料指标也不是这次修改的真实模型质量成绩。未运行生产模型、向量回填或全库重新处理。

真实效果需要在同一资料快照、同一范围下比较结果，开发问题和保留问题分开。开发问题可以含公司名/代码与主题改写；保留问题应覆盖其他公司、主题、时间过滤、比较题、无关/资料不足情形。盲评分别记录前几项相关性、漏掉的已知依据、是否保留互补和分歧、整合是否超出证据、引用能否回到支持它的原文。没有实际可比的检索输出和回答时，不编造 A/B 答案或真实准确率。

## PR56 与主线的整合边界

PR56 先在 `2264b071` 选择性吸收 PR65；本轮再整合已含 PR65、PR60、PR66、PR67 的 `main c57705e`。以下是最终组合行为，不将上游单独的测试成绩当作本组合验收。

- 指定文章且合格正文不超过 6 万字时，模型上下文不再沿用页面的 40 块上限；页面仍最多列 40 块，只有真正读全才标记全文。
- 广范围向量召回先过取 4 倍近邻，再按精确的文章/块号对重新校验当前来源证明、模型、文本哈希及实体约束。不足时，对合格范围做精确距离排序；文章和目录范围直接走该路径。HNSW 调参只作用于当前事务。
- 批次向量失败时，先区分服务不可用和单块失败。每次发送原文前重读并验证来源和文本，写入也带当前哈希及资格条件；坏块或发生变化的块本轮跳过并明确报告，不让它堵住后续块。该命令仍须显式执行，读取页面不会回填。
- 检索页说明语义通道未启用、暂不可用或索引尚未齐全。覆盖率只计算当前可召回的合格块和当前模型，不计过期、孤立或其他模型向量；缓存按数据库主机、端口、库名和模型隔离，最多保留十分钟。这不是问题级召回率。
- 实体 SQL 与 Python 共用大小写敏感别名表，保留短字母别名及词边界规则。普通 `cost/Cost` 不再作为代码 `COST` 的证据，明确 `COST`、中文公司名和品牌名仍可命中；含点号等符号的别名按字面匹配，不把任意分隔符当成等价公司证据。

本轮保留主线已有的有界冷启动等待：普通或刚失败后的查询最多 4 秒，超过 240 秒未成功调用且没有近期失败时最多 15 秒，并受既有配置上限约束；失败后暂停 60 秒。此前选择性整合暂缓该逻辑的记录不再描述本组合。仅用离线时钟与假服务验证，不代表实测延迟，也没有修改模型配置。标题保留 PR56 的精确实体、完整命中 ID 与分页实现。CI 保留主线合并为单作业的节省方案，并将检索相关路径覆盖全部产品源码、测试和依赖；草稿仍跳过，不将 skipped 当通过。

本轮最终组合 1093 项单测通过、1 项回环测试受既有限制未运行，34 项固定原生 PostgreSQL 回归通过；涵盖 SQL/Python 别名边界、当前模型/块哈希、翻译检索、来源调度及同话题归并的缓存保护。所有向量及生成均为假函数；不代表完整集成套件、真实语义召回、生成质量、生产性能或历史恢复验收。先前 `2264b071` 的 1051/12 是另一提交的记录。

同话题可以合并目录归属，但旧观点仅在来源、正文、标题、日期、OCR 哈希、元数据证明及内容哈希均一致时转移，且不改写观点哈希；否则保留在原重复记录待核。昵称只影响显示，不授予星球资格。正文相似或标题/日期规范化也不能将旧模型缓存伪装成当前输入。

## 回填推进与完整 CI 收尾

候选 SQL 只作粗筛。逐块 Python 复核拒绝整批时，本轮记录拒绝键并继续取后续候选；只有候选队列为空才结束。OCR 词都出现但整句错序/跨段的块仍不发送，资格变化和返回后的重验也保留；跳过仅限当前显式运行，不修改原文或放宽下一轮证明。

历史标题/评论修复改变内容哈希后，旧观点、摘要和译文保持原哈希而失效，不能冒充当前输入。完整集成夹具现在显式区分已验证作者、未知/网友历史记录和测试合成材料；`sample` 标记不授予身份，昵称不授予资格，GET 即使带旧自动开关仍不排队生成。

合成排名语料只使用能按当前资格规则入选的正例来源，未知星球资料不再被标为应召回正例。作者预设对照改用启用的非星球来源「黑黑无常」，保持原分布权重、全部基线数值和2%容差；没有降低指标来追绿。星球账户、来源和 OCR 负例由独立原生测试覆盖。此合成排名基线仍不代表真实语义或生成质量。

## 以前的问题

- 检索页用 `websearch_to_tsquery`。不带空格的中文整句会被当成一个连续短语，「腾讯广告加载率」搜不到写着「腾讯的广告加载率」的文章，「苹果定价权」搜不到「苹果在高端手机上的定价权」。只有手动加空格才命中。
- 问库把问题的所有词用「或」连起来，按 `ts_rank_cd` 排序。这个排序不看词有多常见，「公司」「数据」「核心」这类泛词和真正的检索词一样重。公司页「问 AI：库里怎么看 X」的预设问题里没有公司名，前 14 段几乎全被泛词段落占满，常常根本没提这家公司。
- 交给模型的材料最多 14 段、约 9000 字，问「按时间梳理」也只有这么多。

## 现在怎么做

### 1. 读懂问题

- 公司用别名自动机认（和提及统计同一套别名），不靠分词。zhparser 会把「看拼多多」切成「看拼 / 拼 / 多多」，靠分词认公司会出错。
- 作者按名字认，认出来就收窄到他的来源。
- 引号里的是必须原样出现的短语，减号开头的是排除词，`or` 把前后两段并成「任一」。
- 剩下的文字交给 zhparser 切词，按词性去掉代词、助词、连词、介词（怎么、哪些、的、和、在），再去掉问句套话（看法、观点、讨论、作者、梳理……）。`multi_short` 补出来的半个词（「护城河」后面的「护城」）只留长的。
- 每个词自成一组，组与组之间是「且」。

### 2. 每个词有多常见

每个词在全库段落块里出现在多少块（df），按 BM25 的公式算 IDF。最常见的几百个词条直接用 `ANALYZE` 记下的比例估（见下面「库变大以后的耗时」），其余的用全文索引数，计数封顶在库的四分之一，超过的已经很常见，精确值不影响排序。结果缓存十分钟。

只有足够少见的词（出现在 6% 以内的块，最多六万块）拿来召回；很常见的词只参与打分。所以库再大，召回也只碰少数段落。

### 3. 召回

几路合并，各路先只取（文章、块号），合并去重后一次取回正文：

1. 全部词组都命中的段落（GIN 索引求交集）。
2. 问到了公司又有别的词：只在提到这家公司的文章里找含这些词的段落。
3. 标题命中的文章取第一块。段落块不含标题，「标题写了、正文没写」的文章不能漏。标题里就有这些词的排前面，其余按时间新的在前。
4. 任一少见词命中。前几路已经够多就不再撒网。
5. 只问一家公司、没有别的词时（公司页预设）：这家公司被深入提及的文章，按年份分层，每年取一批，深入的优先。
6. 什么检索词都没有时（作者页预设、「汇总这一天」）：范围内各篇的开头两块，新的在前，谈到具体公司的优先。

每一路先在索引命中里封顶取两万块再排名，常见词在大库里也不会拖慢。

### 4. 打分

- BM25：词频按原文逐字数（中文按字面，英文按词边界），文档长度按块长归一。公司按别名数，权重是普通词的 1.5 倍。
- 覆盖率：问题里的词组命中得越全分越高（乘以 0.1 + 0.9 × 覆盖率²）。只命中一个词、但把它重复很多遍的段落排不上去。
- 标题写到的词算进这篇每一段的上下文，但只算半个覆盖。
- 相邻两个词在原文里也连着出现（「渠道」「库存」→「渠道库存」）加分。
- 段落谈到问的公司、所在文章是标题或全文深入谈它的，加分；只在一带而过的文章里出现的，减分。
- 问「最近」时按发布时间加权；问到某一年（「2024 年」）时偏向那一年。

### 5. 挑选

- 低于榜首 12% 的不要；全词命中的段落已经不少时，只命中一半以下的也不要，免得用噪音填满名额。
- 每篇封顶 2～3 段。一篇里有 4 段以上得分在榜首一半以上（几十万字的长研究），这篇封顶放宽到 3 倍；短文照旧。
- 梳理类问题（梳理、变化、历年……）和只问公司的，按年份轮流取；「哪些作者」类按作者轮流取。问「最近」时不摊年份。

- 同一段话出现在两篇里（整段引用、没认出来的转发），只给一次，不占两个名额。

份量按用途：问库页马上列出的「相关原文」40 段；一次交给模型 80 段、约 6.4 万字；资料多时分批读，最多 240 段、18 万字。

### 重复、译文和图片里的字

- 认成重复的那一份（见 [ingest.md](ingest.md)）不切块、不记提及，所有召回都只用主版本。
- 英文文章的中文译文也切块，和原文的块放在同一张表里（`lang = 'zh'`，块号从 10000 起），带对照页的段落锚点。译文的标题和正文另有文章级全文索引。中文问题能直接找到英文文章，结果和引用显示中文译文那一段，点进去是对照页上那一段。同一篇的原文块和译文块都召回时只留译文块。
- 图片里识别出的字也切块（`lang = 'ocr'`，块号从 20000 起），锚点指向文章页上那张图，见 [ocr.md](ocr.md)。

### 6. 交给模型整合

问库提交后先列出相关原文，模型在后台整合，回答页每几秒问一次状态，写完自己刷新。不在一个请求里等模型：站点在 Cloudflare 后面，单个请求大约 100 秒就会被断开（524）。

后台整合的步骤：

1. 让模型给问题里的检索词补同义说法（「护城河」→「壁垒」「竞争优势」），只输出 JSON。同义词并进原词所在的组，权重 0.7；模型补充的新词单独成组，只加分、不计覆盖率。
2. 用扩充后的词再检索一遍，这次取 240 段以内。
3. 一次读得完（6.4 万字以内）就一次作答；读不完就按 4.8 万字一批分批摘录要点（每条带原始编号），三批并行，最后汇总成回答。摘录、同义词扩展和汇总都用配置的推理强度（默认 `xhigh`）。
4. 写回回答和出处，再记下各步耗时、读了多少段、分了几批、模型给的同义词（`llm_answers.stats`）。进程重启时没写完的标成中断，回答页可以「重新整合」。

### 引用核对

模型被要求每句带 `[n]`，回答写完之后逐句再对一遍，纯规则，不再调模型（`src/researchlib/citecheck.py`）。对不上的句子列在回答下面「没核对上」：

- 引用了不存在的编号；
- 句子里的数字（两位以上、带小数、百分比、倍数）在所引段落里找不到；
- 引号里的话在所引段落里找不到；
- 点了某位作者的名，所引段落却都不是他写的；
- 写了具体日期，和所引段落的发布日期、正文都对不上；
- 和所引段落几乎没有一样的说法（引错了段）。

查出来的是「回原文核对一下」，不一定是错。`/api/v1/answers/{id}` 和 `POST /api/v1/ask` 的返回里也有 `checks`。

### 用真实问题评测

下面的合成语料覆盖不到真实的问法和作者真实的用词。回答页上每段原文可以标「不相关」（再点一次取消），也可以在「漏了哪篇」里贴文章链接或编号。标注存进 `answer_feedback`。改了检索、或者库变大了，跑：

```bash
docker compose exec app research-eval-feedback
```

按当时的问题和范围重新检索一遍，报告漏的文章现在找回几篇、标过不相关的段落还剩几段，最后附上近期整合的中位耗时、分批次数、同义词扩展为空的次数。默认复用当时模型给的同义词，不再调模型；加 `--expand` 重新问模型，加 `--json` 输出 JSON。

### 超长文和飞书目录

林文丰的「拼多多投资研究」主文清洗后 76 万字、1341 块，底下还有 41 篇子资料。以前有三处卡住它：

- 每篇最多切 400 块，主文只有前 30% 进了检索。现在上限 9000 块（译文块号从 10000 起，不能撞）。
- 「只问这篇」从开头按顺序取 6 万字，不看问题。现在全文 6 万字以内照旧整篇给；更长的在这篇里按问题检索（关键词加语义），命中的块按原文顺序给，并附上这篇的全部章节标题，模型知道自己看到的是哪几章、没看到哪几章。没有具体问题（「概括这篇」）时后台分批按原文顺序读，最多 24 万字。页面上的「相关原文」只列前 40 块；交给模型的以前也截在 40 块（两万字出头），两万到六万字的文章后半篇模型读不到，又被当成全文、不附章节目录，问到后半篇只能答「没有」。现在交给模型的只按字数截。
- 命中的那一块只有几百字，论证常跨两三块。交给模型时（不是页面上的列表）给命中块补上同一篇的前后块，写成「（上文）……（命中段）……（下文）……」，仍用这条资料的编号引用，引用核对也把前后文算进去。全库提问时前后文最多再占预算的 30%，只问一篇或一个目录时占一半以上。

飞书文库树上每篇都有「问这篇」，有子篇的还有「问这个目录」（`/ask?tree=<文章 id>`）：只在这篇和它在目录树下的全部子篇里检索，每篇封顶放宽到 12 段，前后各补两块，资料前面列出目录下各篇的标题。

### 语义检索

关键词检索找不到「意思对、字不对」的段落：搜「costco 商业模式」，讲 Costco 会员费和低毛利、但没写「商业模式」四个字的文章只能排进部分命中，没点 Costco 名字、讲会员制仓储零售的文章完全搜不到。问库让模型补同义词能补上词级的说法（护城河 → 壁垒），补不上概念级的对应，也太慢，搬不到搜索框。所以加了一路向量。

- **向量服务**：OpenAI 兼容的 `POST /embeddings`，地址和模型在 `.env`（`EMBEDDING_BASE_URL`、`EMBEDDING_MODEL`、`EMBEDDING_API_KEY`）。推荐在 macOS 本机跑 Ollama 的 `bge-m3`（中英双语、1024 维）：Docker 里用不了 GPU，本机的 Ollama 能用苹果芯片的 GPU，容器经 `host.docker.internal` 调它。换成云端 API 只改配置，维度要是 1024。
- **存储**：`chunk_embeddings`（主键文章 + 块号），pgvector 的 `halfvec(1024)` 加 HNSW 索引，一块约 2KB。向量的输入是「标题 + 章节标题 + 块正文」。表不挂外键到段落块：重切块时没变的块凭 `text_hash` 认出来，不重算。表由显式 `research-maintain` 或相关处理命令建立（数据库装了 pgvector 才建），不由 Web 启动创建。
- **回填**：`research-embed` 补算缺的和字改过的块，删掉已经没有对应块的向量。夜间补齐每晚跑一次（`EMBED_LIMIT`，默认 5 万块）。第一次全库回填可以手动跑：`docker compose exec app research-embed`。
- **召回**：问题算一次向量（缓存 256 条），取合格范围内的候选并入关键词通道。广范围使用近邻过取及逐块复核，不足时精确排序；明确公司时保留实体约束，不另取不限公司的候选。关键词候选补相似度时也必须满足当前模型、哈希和来源证明。
- **融合**：相似度按排名折成 0～1 的语义分（第 1 名 1 分，第 60 名以后 0 分，比最相近的差出 0.15 的也是 0），不直接用余弦值，因为不同模型的尺度差很多。关键词分按候选里最高分归一，最终分 = 0.65 × 关键词 + 0.35 × 语义，再乘时间加权。语义分 0.6 以上的段落覆盖率按语义分算，挑选时不会因为没写全词被筛掉。
- **检索页**：词没写全、但语义分够高、问到的公司又确实提到了的文章，排进前面那一档，卡片上标「语义相关」。标题里写没写到问的公司和词，和数段落用同一套规则（公司按别名数，英文按词边界）；以前按子串找，「COST」（开市客的代码）算进了「The Cost of AI」，「DIS」算进了「Disruption」。
- **只在有具体内容的问题上用**：「汇总这一天」「库里怎么看腾讯」这类预设问题不走向量。
- **出问题不拖垮检索**：没配服务、数据库没有 pgvector、服务连不上时只用关键词；连不上后 60 秒内不再试。查询向量 4 秒超时；超过 4 分钟没算过时放宽到 15 秒：本机 Ollama 闲置 5 分钟就卸下模型，重新加载要几秒，以前隔一阵后的第一次搜索总是超时，接下来一分钟也都只按字面找。刚失败过不放宽，服务真卡住时每次搜索最多多等 4 秒。
- **检索页上说明状态**：带具体词的搜索，语义这一路没用上时（没配服务、没装 pgvector、服务连不上、向量一块都没算）在结果上方说一句「这次只按字面找」；向量算了不到 98% 时报出已算和全部的块数（十分钟数一次）。以前这些只在日志里，搜不到按意思相关的文章时分不清是没配、没算还是真没有。

语义这一路的效果要在真实库和真实模型上看：上面的合成评测语料是按词造的，测不出语义。上线后拿 `research-eval-feedback` 和回答页的「漏了哪篇」看。

## 评测

`tools/retrieval_eval/` 里有一份可控的评测语料生成器和评测脚本。语料按作者、年份（2019～2026）、公司、主题生成，每段带真值；正文里混了大量「公司、数据、核心、时间」这类套话，主题用同义说法（护城河 / 壁垒 / 竞争优势 / 门槛），还有「比如腾讯」这种顺带提及。

6000 篇、41,929 个段落块上，改前改后：

| 用例 | 问库准确率 改前 → 改后 | 年份覆盖 改前 → 改后 |
| --- | --- | --- |
| 方伟最近怎么看拼多多的护城河 | 43% → 95% | 2/8 → 8/8 |
| 腾讯广告加载率 | 100% → 100% | 5/8 → 8/8 |
| 茅台批价和渠道库存 | 50% → 100% | 4/8 → 8/8 |
| 苹果的定价权 | 54% → 100% | 4/8 → 8/8 |
| 公司页「库里怎么看腾讯」 | 8% → 100% | 1/8 → 8/8 |
| 作者页「近期核心判断」 | 46% → 100% | — |
| 12 个用例平均 | 68% → 100% | |

改前每题最多 14 段，召回率普遍在 6% 以下；改后交给模型 80 段，资料多时 240 段。

检索页（前 20 篇的准确率）：改前 7 个关键词查询里 5 个一篇都搜不到（「腾讯广告加载率」相关文章 203 篇，搜到 0 篇）；改后 7 个都能搜到，前 20 篇全部相关。

模型补同义词的效果（用固定的同义词模拟模型输出，240 段）：「方伟怎么看拼多多的护城河」召回率 66% → 98.5%；「苹果的定价权」75% → 83%，准确率 90% → 100%。

重跑：

```bash
createdb research_eval
psql research_eval -c "CREATE EXTENSION zhparser"
python3 tools/retrieval_eval/gen_corpus.py --articles 6000
python3 tools/retrieval_eval/evaluate.py
```

生成器只写名字以 `research_eval` 开头的库。改了检索之后跑一遍，看准确率和耗时有没有退步。

CI 用 1500 篇的语料（固定随机种子）跑一遍，和 `tools/retrieval_eval/baseline.json` 比。PR 和 main 上的 push 只在改了检索相关的文件时跑（清单见 `.github/workflows/ci.yml` 里的 `retrieval`），每周一和手动触发时照跑。任何一个用例的准确率或召回率比基线低出 2 个百分点就失败。检索改好了、数字变高了，本地跑 `evaluate.py --json tools/retrieval_eval/baseline.json` 重写基线，和改动一起提交。耗时只打印不比，CI 机器的快慢每次不一样。

## 库变大以后的耗时

把 6000 篇的评测语料复制成 7 份（42,000 篇、29 万个段落块），同一台机器、纯 Python 版 psycopg（正式环境用的二进制版取数更快），2026-10 和改前对比：

| | 改前 | 现在 |
| --- | --- | --- |
| 问库检索（15 个问题，热缓存） | 0.06～1.1 秒 | 0.06～0.6 秒 |
| 检索页（10 个查询，热缓存） | 0.4～1.5 秒 | 0.35～0.8 秒 |
| 数据库刚重启、系统缓存清空后的第一次（7 个查询） | 2.6～3.8 秒 | 1.2～2.3 秒 |

最慢的是全是常见词的问题（「管理层激励」「公司的核心数据」），改前 0.9～1.5 秒，现在 0.4～0.6 秒。12 个用例的准确率、召回率、年份覆盖，检索页前 20 篇的准确率，在 6000 篇和 42,000 篇上都和改前一样。

改了这几处：

- **常见词的块频不现数。** 一个词出现在多少块里（算 IDF 用），以前每个词都用全文索引数一遍，越常见越慢：「数据」在 29 万块里冷缓存要 10 秒以上。现在先查 `ANALYZE` 记下的最常见词条和比例（`pg_stats.most_common_elems`），常见词直接用比例乘总块数，4 毫秒，和实数差 3% 以内；不在里面的少见词照样去数，少见词数起来本来就快。
- **短语去掉切词补出来的子词。** `multi_short` 让「护城河」切成 `'护城河' <-> '护城'`，带位置的短语查询要回表逐行核对位置。两者在索引里总是挨着出现，只查 `'护城河'` 结果一样，全文索引直接答：「护城河」110 → 59 毫秒，「管理层」475 → 155 毫秒。
- **标题单独建索引。** 「标题命中」这一路以前按整篇文章的 `ts_rank` 排，常见词能命中几万篇，逐篇解压整篇的全文向量（300 毫秒，统计信息过期时几十秒）。现在文章和译文的标题各有一列全文索引，标题里有的排前面，其余按时间新的在前：1～2 毫秒。
- **库的平均块长抽样估。** BM25 要库的总块数和平均长度，以前全表扫一遍（29 万块 0.5 秒）。块数超过 5 万后，总数取表的估计行数，平均长度抽两万行左右算：20 毫秒。

还剩的开销：每一路召回先按 `ts_rank_cd` 给候选段落排名（常见词多的问题每一路最多两三百毫秒），再在 Python 里逐段算 BM25（几千段七十毫秒左右）。库到十万篇以上（七十万块），再考虑专门的 BM25 索引或者按年份分区；现在还用不上。

常见词的块频靠统计信息，只在块数达到 5 万以后才用。更小的库（包括 CI 的 1500 篇评测语料）词频按实数计：导入中途 autovacuum 可能先 `ANALYZE` 到一半，比例还是当时的、块数已经是现在的，乘起来 IDF 会漂，同一份语料排序能差出十几篇。大批导入或从备份恢复之后，大库上 autovacuum 要过一阵才会 `ANALYZE`，这期间常见词退回去数，慢一些；可以手动跑一次 `ANALYZE`。

问库的总耗时主要在模型整合（`xhigh` 推理，以分钟计），检索不到一秒。

2026-10 加了去重、歧义别名规则和译文检索之后重跑：各用例的准确率、召回率和改前一致（方伟 + 拼多多 + 护城河 95% / 58%，其余 100%），耗时在同一量级。复制评测库来跑时要记得带上库级的 zhparser 设置（`CREATE DATABASE … TEMPLATE` 不会复制 `ALTER DATABASE … SET`），否则重切出来的块分词不同，召回会掉。
