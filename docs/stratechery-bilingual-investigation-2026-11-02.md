## 3. 根因一：把数量当成对应关系，去重还能掩盖中段缺失

### 最小复现 A：4／3 被凑成 3／3，静默错配

```text
源文：A、A、B、C
译文：甲(A)、另一种措辞的甲(A)、丙(C)   ← B 漏译
预期：不能确定配对，保留两边并提示无法对齐
实际：A↔甲(A)、B↔另一种措辞的甲(A)、C↔丙(C)
```

样例中 A 为 105 字符的英文，两个甲译段均不到 80 字。`pair.py:307` 的 `_best_blocks` 对两边各自去重，再按 gap 更小选择候选；`:128` 的长段去重删掉英文第二份 A，却不删两个短且措辞不同的甲。于是原始叶子 **4／3** 被当成展示叶子 **3／3**。

`display.py:114` 只检查已经整理后的叶子，没触发 #212 的分开展示；`:45` 的完整性检查使用词、链接、媒体和结构的**集合**，重复次数及源段对应关系没有进入校验。所有独有词仍在，`projection_gaps=[0,0]`；页面无提示，QA 为 **PASS、fineGap=1、displayGap=0**。对应探针 `dedupe_hides_a_missing_middle`。

### 最小复现 B：等长但调换段落，写入也不拦截

```text
请求：英文 A(10美元)、B(亏20美元)、C(现金30美元)
模型替身响应：[甲(A), 丙(C), 乙(B)]
实际：返回 translated，写 complete=true；页面 B↔丙(C)、C↔乙(B)；QA PASS
```

`service.py:62` 的校验只看等长／非空，`segments.py:1196` 只看总叶子数；`pair.py:432` 仍按下标配对。不存在能回溯到本次源段的持久清单。此例是**响应错序被系统接受**的证明，不是对真实模型发生频率的测量。

QA 不能作为独立语义门禁：它复用被去重后的配对，且 `display.py:70` 验的是“已存两份文字是否仍在页面”，不是“中文是否译自这一段英文”。出现同样数量的漏段＋补段也受此限制。

## 4. 根因二：保真检查失败仍继续写，且近重复复用会改坏正确响应

### 最小复现 C：正确的 20 被程序覆盖成 10

源文是两段 173 字符的英文，只有结尾金额不同：

```text
... regional commercial advantages; quarterly profit was 10 dollars.
... regional commercial advantages; quarterly profit was 20 dollars.

模型替身正确输出：...本季度利润为10美元。／...本季度利润为20美元。
入库结果：         ...本季度利润为10美元。／...本季度利润为10美元。
```

`service.py:281` 的 `reuse_duplicate_sources` 将 `repeat_key` 后的字符串按前 48 字符归组；`segments.py:1220` 的 `same_repeat` 接受前缀或相似度 ≥0.96，随后直接复制第一份**完整中文 HTML**。金额不同的长段仍被判为同一源段。模型不是此例的故障来源。

实际 `translate_article` 内存入库得到 complete=true。#212 保留了英文中的独有数字 20，最终页面两对分别显示 10↔10、20↔10；但 QA 使用旧的细分配对只统计到一对，仍为 PASS。**保住英文数字并不等于修好了中文数字。** 探针：`near_duplicate_reuse_overwrites_a_correct_amount`。

### 同一写入问题的资源复现

- 两份英文可见文字完全相同，资料链接分别为 `https://example.invalid/one` 和 `/two`。模型按协议都返回 `<a id="L0">优势</a>`，`unshield` 本可分别恢复正确链接。后续近重复复用又把第二份中文的 `/two` 改成第一份 `/one`。这是 **service 写入阶段**的问题；与 #212 已修复的 **display 把已存不同中文链接去重丢失**不同。
- 一段英文含行内 `<code>rate = 42</code>` 和合成图片。模型漏回两个占位符时，`segments.py:1327` 正确返回 None，表示还原失败；`service.py:355` 却执行“None 则保留原模型文字”，随后计入 done 并写 complete=true。中文存储失去代码／图片，QA 仍可 PASS。`display.py:55` 只保护没有可译叶子的顶层块和纯数字表格单元，没覆盖可译段内部的受保护代码。页面可以把共享图片只放英文侧，但这不应许可中文存储无声丢掉行内代码；中文单独模式也会受影响。

仅在探针进程中把 `reuse_duplicate_sources` 替换为恒等函数，前述金额和不同链接两例均恢复正确。**这是局部因果验证，不是已提交补丁，也没有解决其他两类根因。**

## 5. 根因三：旧译文只绑定原始内容，未绑定实际清洗／分段产物

`service.py:111` 注释明确写“清洗规则变了不该把已有译文判成过期”。因此 `_render_original` 即使返回不同 HTML，仍对同一原始 title／body_md／published_at 计算相同 hash。这个 hash 能识别原稿变更，不能识别翻译输入的变更。

离线例子以替身模拟旧 cleaner 保留归档头，随后运行当前真实 cleaner：

```text
相同原始 Markdown：标题、- source: member-rss、正文A、正文B
旧渲染：归档列表、正文A、正文B → 3叶
当前渲染：正文A、正文B        → 2叶
两次 content_hash 完全相同
```

当前待译 SQL `service.py:495` 遇到 complete＋相同 raw hash 即排除；页面 `web/routes.py:777` 用相同条件认为完成。译文表没有当时源文快照、分段版本／清单、cleaner 摘要、prompt 版本或模型回执，不能仅凭这些字段证明 2 叶现文对应 3 叶旧译文。粗分段重检主要抓很大的段数增长或巨型结构，不会覆盖任意少一段、等长错位或金额覆盖。

Stratechery 对此尤其敏感：归档格式包括引文、列表、脚注整份纯文字＋带格式副本；`nested_copies.py:25` 有意只在原文单看／Markdown API 折叠，翻译输入和双语页不折叠。三份独立合成样例均可观察到 raw=2 叶、折叠后=1 叶。`housekeeping` 的 #199／#206 同样有展示／检索／旧译文差异。这些改动本身有避免旧位置漂移的理由，但没有消除版本兼容问题。

### “整篇一大块”的两种来源

1. **#212 的完整性回退**：`display.py:96`／`:114`／`:140` 不敢配时分别显示完整英文和完整中文，带明确提示。探针用 25／24 段得到两块全文；英文块约 2764 字。它保住资料并停止显式硬配，但不是逐段阅读已修好。此时 QA 仍按潜在细分对计 maxEnChars，可能只有约 110，只有 leaf-gap WARN，实际巨块与统计不一致。
2. **旧粗分段兼容模式**：`pair.py:368` 如果关闭 br／句子细分更容易凑齐，便选粗模式。探针细叶为 25／1，粗模式为 1／1，最后是一对 **2764 字符英文**，页面没有 fallback 提示；硬 QA 此例会报 giant-pair FAIL。#212 不重写旧译文，所以仍可能出现。

用户看到“大块”需要先分清以上两种；不能单凭大块断言仍在漏内容，也不能说大块保全了就算对齐成功。

## 7. 最小修复顺序与验收

以下是待实施计划，本轮没有发布或修改产品源码。

### A. 先阻止新错误入库，不动历史数据和付费队列

1. 取消写入阶段的近重复源段复用；若必须复用，只接受完整源片段及链接、代码、媒体完全一致的条件，在各自槽位重新还原资源。不同金额／否定词／资料链接绝不能因为相似度高而覆盖。
2. `unshield` 为 None 时拒绝本次结果或进入明确失败状态；不再把原始模型文字作为已还原成功。写入前逐槽检查受保护资源，而非仅总叶子数；失败不覆盖已存好版本。
3. 这些是确定性校验，先用本报告的金额、链接、行内代码样例做回归；不需真实模型，不能以重试付费请求代替校验。

### B. 配对与 QA 不再靠凑条数恢复位置

1. 缺少可验证源段映射时，原始结构有差额即回退并标为对应关系未知；不要因单侧去重缩小 gap 就恢复位置硬配。确有导出重复的折叠要有对应来源和保真证据，不能只看相同数量。
2. QA 对实际 `article_pairs` 结果统计巨块、notice、段级保真；同时单列原始结构差额和配对可信度。回退保全资料可算“内容保留”，不能算“逐段对齐 PASS”。
3. 写入／读取共用有序源段清单：快照摘要、段 ID、顺序、DOM 路径／重复出现序号、源 HTML 摘要及资源签名；响应按显式 ID 回填，拒绝缺 ID／重复 ID／未知 ID。段 ID 不能只对文字哈希，否则两个同文不同链接或重复出现的段仍会冲突。
4. **ID 也不是语义正确的证明**：模型可能给正确 ID 配错误译文。对固定验收样本另有人工标注的映射和事实（金额、实体、否定等），不能只检查模型回显的 ID。

### C. 将版本兼容和旧数据修复分开

1. 保留 article raw hash 的现有含义；新增实际 canonical 翻译输入／manifest 摘要、cleaner／segmenter／prompt 版本、模型和验收状态。新译文记录这些信息，读取时判定版本是否兼容。
2. 旧稿缺 provenance 先标对应关系未知，保留原始存储和完整回退；**不因版本升级批量置 complete=false 或自动重新排入夜间付费队列**。
3. 在明确的只读快照上区分：仅展示问题、可由清单重建的结构问题、译文本身确实错／缺。可确定的结构修复先做副本比较；无法从已存数据恢复语义的才点名列出重译数量、费用、原版本保留及验收条件，再另取授权。

验收最低要求：

- A／B／C 每一段都对应人工标注的同一来源段，不接受“长度相等即可”；删 B 并插 A、交换 B／C、同数补段、不同数字／否定／链接均能识别或明确降级。
- 比较**有序、带出现次数和资源归属**的源内容与最终投影；不能只比全局词集合、段数或汉字比例。金额／链接必须保留在正确段，表格行列和列表层级不改变，行内代码／独立图片／非译块有明确保存及展示策略。
- 引文／列表／脚注、inline HTML、br 长段、纯数字表格、图片、同文不同链接和重复实例都有固定样本；桌面／手机只验证布局，不能替代上述对应关系检查。
- 旧版本结构变化时不得继续静默标“已对齐”；没有付费授权不得启动批量重译。真实个例验收需绑定部署提交、原始／canonical 输入和存储版本，保存脱敏的逐段结果及未验收项。
