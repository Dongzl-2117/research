# 站内译制（中英对照）

英文原文入库后，由 **investment / research 站内** 调 LLM 翻译（默认 Grok OAuth，`RESEARCH_LLM_PROVIDER=deepseek` 切回 DeepSeek），排版对齐 AIHOT 文章页：

- 默认 **对照**：每段英文在上（小一号、次要色 `--ink-4`），中文在下
- Tab：**对照 / 中文 / 原文**（`/articles/{id}`、`/zh`、`/original`）
- 媒体与图片只在英文侧出现一次
- 下载来的外链图（`article_images.remote`，见 [ingest.md](ingest.md)「外链图片」）不进译制原文和回执：译制时照没下载写成「[外部图片已省略]」，对照页也按这一份核验，显示时再把译文里的占位按顺序换成原文的图（`translate/remote_media.py`）。图在译完以后才下下来，对照照常逐段，不会退成两份全文；占位个数对不上（模型丢了句中的占位，或者正文 HTML 里的 `<img>` 没下载时不留占位）就不换，对照照旧显示占位，「原文」页仍有图
- 默认 `grok-4.7`：`reasoning_effort=high`、`fast=false`、上下文 50 万 token、输出至少 128000。`RESEARCH_LLM_PROVIDER=deepseek` 时用 deepseek-flash：thinking、`reasoning_effort=max`、上下文 1M、输出至少 393216。常量在 `researchlib/deepseek.py` / `researchlib/grok.py`，问库、摘要、观点、论点、双语抽验、样卡走同一套。已经译完（`complete` 且原文 hash 没变）的不因为换提供方重译；没译完的接着补，回执里没变的段复用

不要站外译完再贴进库。译文表是 `article_translations`，按 `content_hash` 与原文对齐。

标题另译一次（存 `title_zh`），失败不影响正文。译文写入后切成中文段落块进检索（`article_chunks` 里 `lang = 'zh'`，带对照页锚点），用中文能搜到、问到英文文章，见 [retrieval.md](retrieval.md)。启动时会给有译文但还没有译文块的文章补切。同一篇的重复不译。

## Grok 凭证（默认；`RESEARCH_LLM_PROVIDER=deepseek` 时不用这份）

Mac mini 上 `docker-compose.yml` 把 `./data` 挂到 `/data`，OAuth 在：

- `XAI_OAUTH_TOKEN_PATH=/data/secrets/xai-oauth.json`
- `XAI_OAUTH_FILE_UID` / `XAI_OAUTH_FILE_GID`：写回后的文件属主，compose 默认 `0` / `0`

几个进程用同一路径和同一 `.lock` 轮流刷新。refresh token 每次刷新都会换，不要复制一份到别处用。Hermes 的 `auth.json` 格式会被拒绝。

问库、`research-digest` 和页面上缺摘要的卡片读的是同一份提供方：默认是 Grok OAuth 的 `data/secrets/xai-oauth.json`。应用启动和部署不会自动跑全库。

## 译制：research-translate

在 Mac mini 上用容器里的命令跑。应用启动和部署都**不会**自动开译制，导入也不会，要自己跑：

```bash
docker compose exec app research-translate --source stratechery --limit 10   # 从待译队列取 10 篇，译完就退
docker compose exec app research-translate --article-id 123                  # 点名，可重复
docker compose exec app research-translate --source stratechery --limit 5 --loop --sleep 60   # 一直跑，队列空了睡 60 秒再扫
docker compose exec app research-translate --loop --workers 4                 # 4 篇同时译，一直跑
docker compose exec -T app research-translate-inventory                       # 只读盘点：各类各有多少篇，见「全库盘点」
docker compose exec app research-translate --from-inventory unmapped --workers 4   # 译盘点清单里的一类
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--source` | 空 | 只译该来源 id；空表示所有来源，中文文章不进队列 |
| `--limit` | 5 | 每轮从待译队列取几篇；`--from-inventory` 时默认整类 |
| `--loop` | 关 | 队列空后休眠再扫，直到 Ctrl-C |
| `--sleep` | 60 | `--loop` 空闲时休眠秒数，最少 5 |
| `--article-id` | 空 | 只译这几篇，可重复 |
| `--fresh` | 关 | 整篇重译，不复用已有译文。默认原文没变的段直接用已有译文，只补没译出来和原文改过的段，见「一段出错不连累整篇」 |
| `--workers` | 1 | 几篇同时译，1 到 16。每篇里的各批照旧一批接一批 |
| `--from-inventory` | 空 | 译盘点清单里这一类的篇（`unmapped`、`stopped`、`legacy`、`old-prompt`……），见「全库盘点」 |
| `--recheck`、`--dry-run` | 关 | 见下面重译旧分段的那一节 |
| `--anytime` | 关 | 走 DeepSeek 时高峰价时段也开新的一篇。默认按队列、按清单译时避开高峰，见下面「避开 DeepSeek 高峰价时段」 |

同一轮里失败过、没有可译正文或者没译全的篇先跳过；`--loop` 时队列只剩它们就先睡，睡醒再给一次机会，不会一直重试同一篇。没配 LLM 凭证时直接退出（退出码 2），不连库。

`RESEARCH_LLM_PROVIDER=deepseek` 时译制走流式。思考模式要是一次把整段响应读完，连接会空等很久，TLS 在中途被拆掉（`UNEXPECTED_EOF_WHILE_READING`），这次已经开始计费，译文一个字都不会入库。`chat_json` 按行读，看到 `data: [DONE]` 才把拼接结果交给对齐；中途断开或流提前结束都丢掉半截，按 2、5、15、30 秒重发同一请求。超时不重试。模型、thinking、`reasoning_effort` 和输出预算不变，失败也不会改走另一家。Grok 译制不流式，一次读完 JSON。连接预算用完仍失败记 `request-failed`，不再把同一批立刻再打一遍。这一篇前面已经译好的段先存下（`complete` 为假，打印 `partial … (request-failed)`），后面的批和标题不再问，下次只补没译的段。一段都没译出来时整篇不入库，和以前一样。标题上的连接失败同样记请求失败，不记成对齐拒绝。

重发同一请求、拆批、先放英文、某一批请求失败，命令行都带钟点（UTC）印在 stderr，例如 `05:12:03 译制请求连了 312 秒断开（SSE 中途断开：…），2 秒后第 2 次发同一请求`。以前这些只写 INFO 日志，命令行没配日志，一行也看不到（2026-11-08 22161、22254 断线时就不知道重发了几次）。重发完还连不上，报错前头写明同一请求试了几次、各连了几秒：`连不上 DeepSeek 接口（同一请求试了 5 次，各连了 312、298、305、290、301 秒）：SSE 中途断开：…`；超时是 `（连了 N 秒，1500 秒没收到数据算超时，不再重发）`。每次几秒、几十秒就断，是网络或接口一时不稳，过几分钟再译多半就好；每次都连了差不多一样久才断，多半是长请求被中途掐掉，再等也一样，那时再考虑把批拆小。

点名的 `--article-id` 里被断线、超时、限流（429）、5xx 打断没译完的篇（打印 `partial … (request-failed)`，或者一段都没译出来、打印 `failed: 连不上…`），以及译的时候原文被别的任务改了的篇（`source-changed-during-request`，11-07 的 22173 撞上夜间补钟点），这一轮最后等 2 分钟自动再补一轮，还没补完再等 10 分钟补一轮（`NAMED_RETRY_PAUSES`），打印「#22161 被打断没译完，2 分钟后再补一轮」。已译的段都存着，再补只问没译出来的段；带 `--fresh` 的照样整篇重译。欠费（402）、鉴权、内容被拒（400）、对不齐这些等多久都一样，不等。补了两轮还没补完，打印「补了 2 轮，#… 还没译完：过一会儿再跑 research-translate --article-id …」，退出码 1。按队列译的不等：没译完的记了冷却（请求失败从 15 分钟起），过了冷却自己回到队列。

跑的时候自动上线先不重建（`scripts/deploy.sh` 看 `docker compose top app` 里有没有 `research-translate`）。它在等的提交 CI 过了，就写 `data/status/.deploy-waiting` 请译制让路：按队列译的（包括 `--loop` 和 `--recheck`）每译完一篇看一眼，在就不再开新的一篇，手上的译完就退，打印「自动上线在等 某提交：不再开新的一篇，手上的译完就退；/health 报出新提交后再跑 research-translate …」（后面是原样的这条命令），下一轮自动上线（10 分钟内）就上了。手上那篇照常译完入库，不会白花钱。上线后要接着译就再开一次，新版本的规则这时才生效；在等上线时新开的会直接停下。点名的 `--article-id` 不让路，译完才上线；只有在等着自动再补的那十来分钟里，自动上线来请它停就不补了，打印上线后要再跑的命令。长时间的 `--loop` 放在 tmux 里跑。

**避开 DeepSeek 高峰价时段**（2026-11-11 加）。DeepSeek 周一到周五北京时间 9 到 12 点、14 到 18 点（UTC 1 到 4 点、6 到 10 点）按高峰价收，别的时段（含周末和国内法定节假日全天）是高峰价的一半（[官方价目](https://api-docs.deepseek.com/quick_start/pricing)，常量 `deepseek.DEEPSEEK_PEAK_HOURS_UTC`）。走 DeepSeek 时，按队列、按清单译的（包括 `--loop`、`--recheck`、`--from-inventory`）到了高峰就不再开新的一篇，手上的译完，打印「DeepSeek 高峰价时段（…）：不开新的一篇，手上的译完；北京时间 12:00 以后接着译」；每分钟看一眼，过了高峰打印「过了 DeepSeek 高峰价时段，接着译」，接着拿下一篇。进程一直不退，外面套的循环不用管；等着的时候自动上线来请它让路，一分钟内照样退出。这一轮的合计行带上「（其中高峰价时段停了 X）」，拿合计算速度时减掉这一段。节假日没认，照样当高峰停。点名的 `--article-id` 照译；高峰也要译，加 `--anytime`。走 Grok 的（订阅里出，不分时段）不看这个。

### 几篇同时译、每篇用了多少（2026-11-08）

一篇里的各批一批接一批：每批带着前面译好的中文当上文，术语和指代才前后一致，所以一篇快不了。全库一千多篇只开一个进程要好几天，`--workers N` 让 N 篇同时译，每个 worker 一条数据库连接、同一时刻最多一个模型请求。每篇开译前占一把 Postgres 会话级 advisory lock（`hashtext('research-translate')` 和文章 id），译完放掉，进程没了自动放掉：同一进程的几个 worker、同时开着的几个 `research-translate`（比如一个 `--loop` 再加一个点名的）都不会同时译同一篇。按队列译的碰上别处正在译的就跳过，译下一篇；点名的等别处译完再接着补（打印「#… 别处正在译这一篇，等它译完再接着补」）。让路照旧：每个 worker 译完手上那篇看一眼自动上线在不在等，在就不再拿新的，几篇都译完进程才退。Ctrl-C 立刻退，正在译的几篇这次不存。

几篇同时译时，stderr 上每一行进度前面带着文章号：`05:12:03 #22161 译制请求连了 312 秒断开…`。每篇的结果行后面接着这一篇的用量和用时（下面的数字只是示意）：`#22161 translated segments=220 reused=204 · 请求 9 次，输入 52,331 token（缓存命中 31,872），输出 61,204 token（思考 50,112），用时 8 分 41 秒`。回答收到了但用不了（不是 JSON、条数不对）的那次也算，断在半路的那次接口没报用量，不算。调过模型的话，停下时再印一行这一轮的合计：`这一轮 2 小时 13 分：译完 37 篇，没译完 2 篇；请求 …`。全是复用、一次模型都没调的篇只印结果。

先开 4 个：Mac mini 经 Colima 转发时并发的 TLS 连接多了出过 `DECRYPTION_FAILED`。跑一阵 stderr 上没有成串的「连了几秒断开」再往上加。`--workers` 会被 `RESEARCH_LLM_CONCURRENCY`（默认 8，没有低硬顶）夹住，同时不能超过 16（每个 worker 一条数据库连接）。和识图全量同时跑时两边的请求加在一起，打的是同一份账号额度。429 打 `rate-limit event=429`。

Grok 走 `https://api.x.ai/v1/chat/completions`，Bearer 为 OAuth access token；过期或 403 stale 时强制刷新再试。长调用默认 25 分钟（`LLM_LONG_TIMEOUT_MS`）。DeepSeek 译制走流式，见上面「DeepSeek 译制走流式」。

### 一次送整篇：`--batch-segments 0`（2026-11-10 加，没试）

11-10 起译制走 Grok（grok-4.7、`high`、不流式），一次请求要等模型想完、写完整批才返回，一次几分钟。一篇按 12 段一批、一批接一批，普通文章四五次请求，要二三十分钟；访谈要一两个小时。和识图同跑时两边抢同一份 Grok 限额，Zhilin 11-10 报的数是 3 小时 16 分译完约 21 篇。

`--batch-segments N` 改一次请求最多送几段，默认 12。`0` 不按段数切，只按 24000 字一批：一般文章一次请求送整篇，访谈这种长文仍分几批。别的都不变：照旧按段编号交回（`id`、`source_hash` 逐项回显），逐段核数字、链接、图片和占位符，哪段不对只重译那一段；对不齐先原批重来一次，再对半拆开。一批就是整篇时不另带 `articleContext`（全文已经在 `segments` 里），拆成两半时两半照旧带上全文。让路以后印出的重跑命令带着这个参数。

12 段的上限是给 DeepSeek Flash 定的，一批段数多了它会少回或多回一段，DeepSeek 照旧用默认值。Grok 一次交回几十段对不对得上、整篇一次送快多少，要实测。11-10 Zhilin 选了剩下的全部走 DeepSeek（见「全部按第 3 版译」），这个参数没试。以后用 Grok 跑大批时，先挑 20 篇还没译过的：

```bash
docker compose exec app research-translate --from-inventory none --limit 20 --workers 8 --batch-segments 0
```

看三样：每篇结果行的请求次数、思考 token 和用时，和长短差不多、按 12 段一批译的篇比；stderr 上「对半拆开重试」和「先放英文」有几行；对照页抽看前后叫法、通顺，长批末尾几段的中英字数比有没有比前面低。对得上、明显更快，再加这个参数跑剩下的。

## Stratechery

全量归档已入库，`config/sources.yaml` 里 `stratechery` 是 `enabled: true`（#61）。盒子上再抓到 Passport 全文 / Daily≥5500 合格稿时：

2. `docker compose exec app research-translate --source stratechery --limit 10`，一批译不完就加 `--loop`

游客半截 / guest teaser **不入库、不译**。

导出的引文、带段落的列表项和脚注都写了两遍：先是一行纯文字（链接、加粗都没了），紧跟着是里面每一段带格式的副本。单看原文时（文章页没有译文、点了「原文」，以及 `/api/v1/articles/{id}.md`）显示前把副本放回引文、列表项，纯文字那份不显示（`researchlib/nested_copies.py`）。库里的 `body_md` 不改，译制、检索、问库读的还是两遍。已有译文是照着两遍译的，原文不能先收（收了就和译文错开），中英对照和只看中文在按位置配好以后用同一条规则收（2026-11-11，`nested_copies.copy_runs`：外层短于 8 个字不认，后面紧跟的几块去掉格式后接起来正好等于外层才算）。好几段的引文，纯文字那份也分段（段间是「>」空行），整条引文算一个外层；对照页上一段一对，连着的几对引文合起来认。带格式那几段中间夹着的图、只剩没字的链接（原文的图包在链接里）和只有「[…]」这种标点的段落跟着放回去，不占字，最后一段后面的不算。带格式那几段里还能有引文、列表（原文的引文、列表项里套着的，导出只写一遍），按整块的字接，一起放回去；引文里套着的引文自己也写了两遍时先收里面那条，外层下一轮才接得上，最多三轮。收好的引文、列表项以后只当别的外层里的一块，不再当外层，正文自己接着写的同一段不会被收进去。连着写两遍的同一张图（只有图的块和紧挨着的上一块是同几张图）三种页面都只留一张（11-11 晚）。对照页上纯文字那一对不显示，带格式的几对套回引文、列表项的外壳，有序列表的序号、脚注末尾回到正文的「↩」链接都在，纯文字那份的段落号留成空锚点；只看中文页在原文上认，译文的顶层块和原文一一对得上时按位置收掉纯文字那份的中文（`translate/display.py` 的 `_fold_copy_pairs`、`fold_translated_copies`）。原文先按译制时的切法（materialize 再并句）落成节点比一次：引文里按行、按句切开译的段，译文里是几个 `<p>`，这样才对得上；再拿原样的原文比一次（切法改过以前的旧稿是照原样译的），哪次收得多用哪次。以前对照页只收 80 字以上的重复，短引文、短脚注左右两栏各出现两次，收长的时还常留下纯文字那份（丢了分段、加粗、链接），只看中文页两份都在。11-11 抽 40 篇译过的文章复核（上一版上线后只看中文页 32 篇还有重复）：原文里剩下的 90 句重复收到 0，没少一个词、一个链接、一张图。收掉的那份的中文只挂页面上还没说过的句子。两份是同一段英文各自译的，同一句常只差几个字：去掉标签、标点后七成以上的字按顺序对得上（短于 10 个字的要整句出现过），或者已经由同一段英文的另几对显示，都算说过，不再挂；带着别处没有的数字、英文词的照样挂，留下那份漏译的句子也照样挂，挂在字对得上的那一段后面（哪段都对不上就跟着前一句），只挂那几句，外面的列表、段落外壳不带过来（2026-11-10）。以前按整句一字不差判断，标签位置不同、少一两个字的同一句都算新句，读者在一对里看到同一句中文两遍；这只改页面，库里的译文不动，改完旧页面一起变好。以后译的也照两遍送进模型。

每日更新照邮件导出，开头的「Listen to this post:」「Good morning,」「On to the Update:」和结尾的播客提示、转发须知（「intended for a single recipient」「order multiple subscriptions for your team」）、「Thanks for being a subscriber, and have a great day!」几乎每篇都有。检索文字和段落块不收这几句，单看原文时也不显示（`researchlib/housekeeping.py`）；「Good morning,」和「On to the Update:」之间作者写的话（更正、回应读者、播客预告）留着。邮件导出的标题行下面常常不空行就跟着「**Listen to this post:**」，标题行单独算一段；2026 年网页导出（`- source: member-rss`）整篇一行一段、中间没有空行，开头的几句按行认，结尾从最后一行往前找最长的一截套话。中英对照和只看中文照旧：已有译文里这几句也译了，对照按位置配，原文这边少几段就和译文错开。以后译的也照旧整篇送。

2026 年网页导出一个文本节点一行：链接字单独一行，后面的「, mostly …」「. After that …」另起一行，小标题也只是单独一行，阅读页上一句话常被拆成三四行。单看原文时（文章页没有译文、点了「原文」，以及 `/api/v1/articles/{id}` 和 `.md`、MCP 的 `get_article`）按行拼回段落（`researchlib/web_export.py`）：句读开头的贴上去，没说完的半句接下一行，访谈的「JD:」和后面那句同一段，小标题单独一段。线上 32 篇试过，3926 行收成 2235 段。中英对照、只看中文和译制读的 `canonical_body_html` 不拼：已有译文是照没拼的原文切段译的，拼了段数就变，对照页整页分开（见 [bilingual-mapping-2026-11-02.md](bilingual-mapping-2026-11-02.md)）。库里的 `body_md`、检索文字和段落块不改。

## 全库盘点：research-translate-inventory（2026-11-08）

只读，不调模型、不写库，几分钟。把英文文章（和待译队列同一条语言规则，重复和隐藏的不算）分成几类，打印各类篇数（按来源分）和英文字符数，id 清单写进 `data/status/translate-inventory.json`。网站不显示的网友帖、「图片」评论壳单列为 `site-hidden`，不算进各类，待译队列也不译（11-08 以前的队列会译它们）。已译完的逐篇渲染一遍页面，分成能不能逐段对照，对不上的打印原因（`displayReasons`）：

```bash
docker compose exec -T app research-translate-inventory
```

## 译制输入：和文章页同一条清洗

译制读的正文先过 `boilerplate.clean_article`，和文章页显示前那一遍是同一条：归档头、引流尾巴、二维码、星球导出脚手架都在送进模型之前去掉。`article_translations.content_hash` 仍按库里的 `body_md` 算，清洗规则变了不会把已有译文判成过期；重检用的原文段数（`list_coarse_translations`）也按清洗后的正文算。

不清洗就会把不该译的行也译出来。Stratechery 周报正文里有一行归档头 `- source: member-rss`，页面早就洗掉了，译制以前照原样送进模型，中文侧于是多一段「来源：member-rss」，英文侧没有，对照从第一对起整页错一行。22092 是这种：英 76 段、中 77 段，77 对里每一对都挪了一位。`- rss_link:` 同样是归档头，和 `- source:` 一起在送译和显示前去掉；以前没认的话，英文侧多一行链接、中文侧仍是「来源：member-rss」，从第一对起错位。

这条只管以后译的。改之前译好的篇目，译文里已经多出这一段，展示层不会自己去补，`--recheck` 也抽不到（22092 记的是 `segments = 2`、正文不到 8000 字），只能整篇重译。待重译的 Stratechery 译文这样点名（只查库，不改）：

```sql
SELECT a.id
FROM articles a JOIN article_translations t ON t.article_id = a.id
WHERE t.complete AND t.content_hash = a.content_hash
  AND t.body_html ILIKE '%member-rss%'
ORDER BY a.id;
```

2026-10-30 跑出来 38 篇，全是 stratechery。其中 14 篇的叶子数正好只多这一段（22092、22198、22240 那种「整页错一行」，中英从第一对起全体挪一位），其余是更早的粗分段写回，本来就该重译。重译要花 DeepSeek 的钱，按篇点名：

```bash
docker compose exec app research-translate --article-id 22092 --article-id 22198
```

重译写回后叶子和页面一致，不用再跑第二遍。

## 段对齐

叶子段和 AIHOT `segmentsOf` 同一条规则：标签在 `p`、`h2`–`h5`、`li`、`blockquote`、`figcaption`、`td`、`th`、`dt`、`dd`、`caption` 里，并且没有块级子节点，才是一段。有块级子节点就继续往下看。所以正文里的大段 `blockquote`（markdown 里连续的 `>`）会拆成里面的段落、标题和列表项；没有块级子节点的短引用仍是一整段 `blockquote`。

AIHOT 的 CONTAINER 不含 `dl`。#119 从 `editorial/translate.ts` 的 `segmentsOf` 移植时就是这样；这份 TypeScript 不在本仓库，公开检索也没有另一份可以对照，所以不把「AIHOT 会拆 `dl`」写成事实。研究站为了对照能读，在这条规则之外多走一步：叶子里的 `dl` 有多条 `dt` / `dd`，或纯文本达到 4000 字时，继续拆进这些子节点。只有一条、而且不长的定义列表仍是一整段 `blockquote`。术语表仍是一条 `dt` 配一条 `dd`。连续四条以上的短 `dt`（markdown 把粘贴的每一行收成一条）按句号收成段，大约一两句一段，不会变成几百个只有几个词的对照，也不从半句中间切开。单条 `dt` / `dd` 如果只是用 `<br>` 把很多行粘在一起、纯文本超过 2000 字，也按句收成段。这样 Stratechery 里被收成 `<blockquote><dl><dt>` 的长粘贴不会再是几万字的一对。

普通段落（`p`、列表项、引用、表格单元、标题）里用 `<br>` 粘起来的很多行，非空行到三个就先按行切开，再按句收成叶子：一行自己已经以句号结尾就单独成段，人名、链接文字这种半句并进后文，直到句末。两行的地址、诗句、署名不拆。不按 180 字把后面的短句再并进来，也不按定义列表那条 700 字的上限从半句切开——中文更短，同一批 `<br>` 会切出不同的组数；切在句末标点前时，剩下的「).」没有字母。这行不单独成叶，并进前一句（前面没有句子就并进后一句）。单独留下的话不会送去翻译，写回把其余行换成 `<p>` 之后再切会被丢掉，英文比中文多一片叶子。写回换成若干 `<p>`（`id="p-N"` 留在第一句上；原来是列表项或引用时外壳还在），译文里不再留 `<br>`。译文没有句号、或者比英文短，也不会被重新并段，再切一次叶子数不变。访谈稿里「super-agent / Ari Emanuel / . Emanuel is…」这种软换行因此是一整句，而不是每个链接各一对。`dt` / `dd` 也不再按 700 字从半句切开：句末才收，下一条已经很长时，前面没写完的「( example.com」留在同一句里，不单独成叶。

没有够三行 `<br>`、但纯文本超过 900 字并且里面有多句的叶子，同样按句切开再写回成若干 `<p>`。译制仍按这些句子 1:1 写入。对照页在投影通过之后，把同一次按句切开的那几句并回原来的段落、列表项或标题，页面上这一对的长度跟原文那一段一样。译文若已经是许多没有分段标记的短段，仍按原文这一次切开的分组并回去。另一段里有一句中文和英文相同、对照不单列中文，不能因此把整页的并段丢掉。`<br>` 粘出来的长粘贴不并回去，避免几万字重新合成一对。网址、小数和 `Inc.` 这类缩写里的句号不当成句末。一整句再长也不从半句撕开。写回之后再切，叶子数不变。切开以后字、链接、图片或代码和整段对不上的，这一段整段留着不切（2026-11-07；`<br>` 粘起来的多行和定义列表里按 `<br>` 拆的段，版本 9 起同样先核再切）：Stratechery 访谈导出时每节末尾留一个空锚点 `[]()`，紧贴在最后一句的句号后面，切开后哪一句都不带它；链接文字里有缩写名（「[J. Q.] Public」）时，句号落在链接里，一个链接被切成两三个。以前这两种段让整篇过不了 `materialize`（`materialize-content`），译制一开始就拒收，以后一直拒；对照页也只能分开展示（「分段无法保真」）。能切开而不丢东西的段照旧切，已经入库的回执不受影响。旧稿候选重排（`split_sentence_paragraphs`）不走这道检查。英文里的 `<a href>` 锚文本留在中英两边；译文只剩括号里的域名时，把同一条链接套回去，不另外再写一个 `(域名)`。

入库时，模型返回的 `t` 必须和这批 `segments` 一样长，再按这些叶子段原位写回（外壳留着，只换那一段）。条数不一致时，先按原批重试一次；仍不一致就把这批对半拆开再译，直到一段对一段。只剩一段还对不齐，这一段先放英文（版本 9 起；以前是整篇不入库），错位的 `t` 不入库。带 `segment_ids` 的请求里，id 或 `source_hash` 没有逐项原样回显、回答不是 JSON、这一批被接口拒（HTTP 400、413、422）也走这一条（#217 之后这条路一度走不到，模型少回一段整篇就作废）。

写回后再用同一套叶子规则切译文，段数必须和原文一样。单看一段就知道写回会多切出叶子的（译文里多了 `<br>` 或段落标签），这一段单独重译；整篇写回才看得出来的（定义列表的打包），二分找出是哪几段，这几段先放英文（版本 9）。模型返回的片段收成一个没有块级子节点的叶子：外层标签按原段留着，多出来的 `<p>` 并回这一段，没闭合的标签补上，避免后文的标题被吞进上一段。连续四条以上的 `dt` 里，单独成段的那一条写成 `<p>` 而不是更短的 `dt`，否则中文变短后会按字数重新打包，对照从这里开始错位。定义列表里用 `<br>` 拆开的段同样各自收成一段，不再按译文字数重拆。展示仍先按这一套规则把原文和译文各切一次、按位置对齐，再把同一源段落并回一对。两边叶子数一致时按位置 1:1；只有两边都收掉同样多的连续重复段，对照才少掉那几段。段数对不齐的旧稿不另做硬配：同一套去重只在差距变小时拉齐，多出来的仍挂在末尾。

默认一批最多 12 段、24000 字符（`--batch-segments` 可改段数，见上面「一次送整篇」）。超过的另起一批；单段比字符上限还长时单独成批，不从中间切开。整篇原文仍放在 `articleContext` 里（放得下的时候），供统一术语，不拿去凑 `t` 的条数。

有原文的段如果译成空白，这一段单独重译，还空就先放英文。译文只要非空就收下，不拿中英字符长度的比例做门槛。

一个译段内部，模型连吐的相同顶层块或相同 `<p>` 会收成一份。原文里同一段正文出现两次（引用后再贴一遍，或列表项后再跟一段同文）时，后一次沿用第一次的译文，写回仍然一段对一段，不删槽位。只在中文侧少了这段的旧稿不回写、不重译。

对照页永不因段数差退中文。展示层对原文和译文各跑一遍与单段相同的连续块去重（忽略 `id="p-N"`）。普通段落按 `<br>` 拆不拆，看拆开后两边的差额会不会变大：旧译文是整段译的，行数常和原文差一两行，拆开只会让对照从那行起整段错开，这时仍整段一对；新译文写回时叶子数一致，拆开就是按句成对。两边叶子段一样多时按位置收，不把两边各自收完再比条数。后一对的英文够长（可见文字大约 80 字以上），和前面某一对相同、只是它的开头、或几乎一样（长度差在一成以内、相似度 0.96 以上），并且这一对的中文也是前面那一对中文的同一段，两对一起收掉。中文译文通常更短，不到 80 字也算同一段；后一对没有译文也收掉。英文重复但中文是另一句的不收，后面的段落也不会因此错位。隔了几段又贴出来的同一句、同一组句子都走这一条，不要求紧挨着。列表项和同文的 `<p>` 也是。只共享开头、后文不同的两段都留着。英文短于大约 80 字的不按这条收。够长的一句若整句包含在另一对更长的英文里，收掉短的那一对，长的留下，后面多出来的句子还在。这一比较只压空白、忽略大小写，不去掉标点，两条来源注释只是括号不同时都留着。中文不必逐字嵌在长段译文里，分开译的两遍措辞不同也收短句。标签边界按空格计，所以正好 80 字的一句不会因为中间套了 `<strong>`、句号贴在标签上就少算一格。较短的一句若有大约四分之三是较长那句的开头，两句长度差在一成以内，中文又共享一长串（大约 12 个字，措辞可以不同），收掉短的，长的留下。只共享大约三分之二开头、后文明显岔开的两份提示仍都留着。英文整句相同、中文却是另一句的，仍然两对都留。以前两边各自按 80 字去收，中文更短就少收几对，条数对不齐就整页退回，隔开的长英文会留下两三次。不一样多时，两边仍各收各的长叶子，只有差距变小才改用那一份，只短一边不硬配。对不齐的多余段挂在末尾：多出来的原文没有译文，多出来的译文没有英文。媒体仍只留在英文侧；译文和原文纯文本相同、或译文为空，这一段不显示中文。模型少段或多段仍然整批重试或拆批，不靠展示层去补条数。

旧译文若还是一整段对着现在按句切开的原文，拆开会让差额变大，对照仍用整段那一份，直到点名重译。重译写回后叶子数一致，才按句并排，重复段也收成一份。

展示层的去重只影响页面，不改变切段：先拿不去重的细对过一遍投影检查，收重复时也只收删了不会丢原文内容的那些对（文字、数字、图片地址、资料链接，以及带属性的列表和表格结构都算内容），收完再核一次原文侧。软去重因此不会把整页打回「整篇英文 + 整篇中文」，也不会吞掉独有的一两个字。只有细对本身配不上（两边叶子条数不同，或未去重的细对投影就丢正文）才退回完整区块；连区块都对应不上，才分别展示完整原文和译文，页面上给出提示。整块对照的页面同样收重复。

已经按旧的粗分段译完、且译文里还留着内层标签的文章，部署后对照会按新的叶子段重排，不必先改库。库里的 `segments` 仍是当时的段数。要按新粒度重译，用 `recheck`：只抽「一个叶子仍包着很多段」或「记下的段数远少于现在能切出的叶子」的完整译文。远少是指块级叶子（不含普通段落里按 `<br>` 拆出来的行）至少多 15 段，并且达到原来的三倍，或多出 40 段。多条定义列表以前整段是一个叶子，会对上这条（21118 在 #119 之后大约记了 180 段，拆开后大约三百多段）。一条短定义列表仍是一段，不抽；一个 `<p>` 里几十行 `<br>` 也不只因为拆了行就抽，那几行本来就是一个整段一段译的。重译写回之后段数对齐，同一篇不会反复出现。

先看会重译哪些（不调模型）：

```bash
docker compose exec app research-translate --recheck --dry-run --source stratechery --limit 200
docker compose exec app research-translate --recheck --dry-run --limit 200   # 全部英文来源
```

确认篇数可以接受再开跑。每篇按新叶子重译，长文大约十几批 DeepSeek。不带 `--recheck` 的 `--loop` 只译还没有完整译文的，不会重跑这几篇。

```bash
docker compose exec app research-translate --recheck --source stratechery --limit 5 --loop --sleep 60
```

点名几篇：`research-translate --article-id 21118`。

#121 之后已经重译过、但写回时把长 `dt` 收成更短结构的文章（21118、21133、21193 这一类），库里的 `segments` 等于那份错误译文的叶子数，`--recheck` 抽不到。部署后只改展示也不能把写丢的叶子找回来，必须点名整篇重译：

```bash
docker compose exec app research-translate --article-id 21118 --article-id 21133 --article-id 21193
```

重译完成前，对照仍会从差额处开始错位（同一段英文开头重复出现、标题配上「外部图片已省略」、文末中文空）。重译写回之后，原文和译文叶子数一致，再打开对照页即可，不必再 force 第二次。

超长多句叶子（21118 的 Wearables / Services 一类两千字列表项加同文段落，22195 的 iPhone Duo 引用大约两千英文字）按句切开之后，同一段英文还会隔开再出现两三次：译文常常不到 80 字，两边各自去重对不齐条数，展示就退回未去重的序列。叶子数已经对齐时按位置收：中文更短也算同一段；短句整句包含在更长的一段里时收掉短句、留下长段。这些重复不必再译。`<br>` 粘出来的长粘贴和隔开的重复堆不应再合成几千字的一对，也不应再有隔开的同一段长英文，或短句和把它包含进去的长段各出现一次。原文本身就是一整段的，对照按这一段并排，不再拆成互不相干的句子。21130 的叶子数已经对齐，近重复段（例如 Meta 开头、Judge Alsup）走同一条。旧稿若还是整段一对，拆开会让差额变大，对照仍用整段那一份，直到点名重译：

```bash
docker compose exec app research-translate --article-id 21118 --article-id 22195
```

差额变大时不会为了拆句把后面的段落错位。

## 对照质量检查：research-bilingual-qa

`research-bilingual-qa` 把人工抽验对照页时看的几条硬指标做成可重复的命令。它按文章页的顺序重算对照：原文同一遍清洗、模板尾巴、md 链接改写和图片文字，译文同一遍白名单，再走 `display.article_pairs`——也就是页面上真正显示的那一份。只判断，不改库、不重译、不跑 OCR。

| 指标 | 代码里的名字 | 判定 |
| --- | --- | --- |
| 整页退回 | `display-fallback-separate` | 展示层分别显示完整原文和译文（`displayNotice` 非空）。细对齐再漂亮，这页也读不出对照，按失败算 |
| 巨型 pair | `giant-pair` | 单对英文可见文字 ≥ 2000 字。按句切开之后不该再有 |
| 近重复组 | `near-duplicate` | 页面上还留着能安全收掉的重复、整句包含或近前缀堆的长英文。收掉会丢原文里的独有文字、数字或资料链接的那一对要留着，不算缺陷 |
| long-empty-ZH | `long-empty-zh` | 对上的那一对英文 ≥ 80 字，中文为空。短行、纯标点可以缺；整页分开展示时英文那一段本来没有中文，不重复点名 |
| 归档头 | `archive-header` | 正文里还留着 `member-rss`、`rss_link`、`- source:` 这类行。`来源：` 单独出现可能是正文里的正常说法，不单独认 |
| 叶子/对数 | `leaf-gap` | 展示硬排的两边叶子差。差 40 段以上按失败算，差一两段只告警 |
| 展示丢内容 | `display-content-loss` | 展示比细对齐叶子少了原文的字、图片或链接。软去重不该造成这个 |
| 展示丢资料链接 | `translation-material-loss` | 展示少了译文里的图片或资料链接。措辞不同的另一种译法被收掉不算 |

任一项失败就是 `FAIL`，只有告警是 `WARN`，都没有是 `PASS`。页面指标（`pairs`、`maxEN`、`giant`、`nearDuplicates`、`longEmptyZh`）一律按页面实际显示的对来算：细分叶子很好看而 `pairs=2`、`displayNotice` 非空，就是整页退回了，判 `FAIL`。报告里同时给细分叶子数（`leaves=英文/中文`）、展示实际用的切法（`display=英文/中文`）和最长一对的英文字符数（`maxEN`）；`preservation.translated` 是收重复时少掉的另一种译法的字数，只看不改判。

```bash
docker compose exec app research-bilingual-qa --article-id 21118
docker compose exec app research-bilingual-qa --article-id 21118 --article-id 22195 --article-id 22092
docker compose exec app research-bilingual-qa --source stratechery --limit 20
docker compose exec app research-bilingual-qa --limit 50 --json --report /data/status/bilingual-qa.json
docker compose exec app research-bilingual-qa --article-id 21118 --llm --llm-sample 1
```

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--article-id` | 空 | 点名，可重复 |
| `--source`、`--limit` | 空、20 | 不点名时按译文更新时间从新到旧取最近几篇 |
| `--json` | 关 | 输出一个 JSON 对象 |
| `--report` | 空 | 另写一份 JSON 文件；`/data/status/` 在宿主机上是 `~/research/data/status/` |
| `--strict` | 关 | 有警告也返回 1 |
| `--llm`、`--llm-sample` | 关、3 | 对没有失败项的篇再跑 LLM 抽验，默认最多 3 篇 |
| `--omissions` | 关 | 段内漏句抽查，不跑硬指标，见下面「段内漏句抽查」 |
| `--from-inventory` | 空 | 和 `--omissions` 一起用：从盘点清单（`research-translate-inventory`）的这一类里均匀抽 `--limit` 篇，新旧都有 |

退出码：0 通过（或有警告但没加 `--strict`），1 有失败项（硬指标，或 `--llm` 时模型给 `fail`；加 `--strict` 时警告也算），2 参数、库或 LLM 的问题。只读：连库走 `db.connect`，不跑迁移、不写表；`--report` 只写你给的那个文件。

### LLM 抽验

`--llm` 用当前提供方（默认 Grok `grok-4.7` / `reasoning_effort=high` / `fast=false`；`RESEARCH_LLM_PROVIDER=deepseek` 时是 deepseek-flash / thinking / `max`），和译制、问库走同一个 `llm.chat`，判断抽样段落是否成对。每篇最多 12 对：先取硬指标点名的那几对，再按整篇的头、中、尾补；每段截到 1500 字并标 `truncated`，提示词里写明截断不算漏译、错位。提示词在 `researchlib/translate/qa.py` 的 `LLM_SYSTEM`，只判断 `misaligned` / `missing-zh` / `duplicate` / `other`，不改写译文。

模型返回 `verdict` / `score` / `issues` / `summary`，打印在报告里，`--json` 和 `--report` 也带上。`--llm` 默认跳过硬指标已经失败的篇，钱先花在看不出问题的篇上。模型给 `fail` 时整条命令退出 1；给 `warn` 只在 `--strict` 时退出 1。凭证不对、接口错、JSON 收不成结论都退出 2，硬指标的结果照常打印。整个命令不写库。

一次抽验十几对、几千字，跑 3 篇费用很小；但不要在启动或部署时自动跑，也不要接进夜间任务全库扫。旧译文失败多，先按篇点名。

### 段内漏句抽查：`--omissions`（2026-11-07）

条数、段身份、链接、数字都逐段核过以后，剩下没有自动检查的是一段里漏译了某句、某个分句、数字或名字。`--omissions` 按回执逐段把英文和中文交给站内模型（同一组 DeepSeek 常量），让它摘出中文漏掉的英文原文：

```bash
docker compose exec app research-bilingual-qa --omissions --source stratechery --limit 50
docker compose exec app research-bilingual-qa --omissions --article-id 22188 --json --report /data/status/omissions.json
docker compose exec app research-bilingual-qa --omissions --from-inventory legacy-structural --limit 50   # 没回执的旧稿抽 50 篇
```

- 段对来自回执 `provenance.segments`，和当时送去译的那一段一一对应，不受对照页并段、去重的影响。先放英文的段（`untranslated`）不送。不点名时按译文更新时间取最近几篇，和别的模式一样。
- 没有回执的旧稿（11-09 起）按页面上并排显示的段对核（`qa.pairs_for_review`，和对照页同一份），打印「按页面配对」。页面分开展示、没有段对的跳过；收起的重复、没有英文字母的对不送；只有英文、没有中文的对（整段没译）不送模型，单独计数（`englishOnly`）。页面配对要是错了位，会成片报漏：一篇报出一大串的，先看对照页是不是错位。要不要为补回执整篇重译旧稿，先用 `--from-inventory legacy-structural --limit 50` 量一下漏句率，和有回执的比。
- 一批最多 12 对、8000 个英文字符。模型摘出来的原文要能在这一段英文里逐字找到（忽略大小写、弯引号、破折号和空白）才计入；找不到的丢掉，记条数（`unverified`），丢掉的摘句本身记在报告的 `dropped` 里、命令行也印出来，看得出是模型改写了原文还是编的。
- 每篇打印 `pairs`、`flagged`，每处漏掉的英文和这一段中文的开头；最后两行是疑似漏句的段数和比例、模型用量（请求次数、输入和其中缓存命中、输出和其中思考 token），按当时的 DeepSeek 价目乘。
- 只读：不写库，不改回执，不拦入库。结果是线索，措辞不同、几句并一句被当成漏的误报，要人看一眼。
- 一批回答用不了（不是 JSON、HTTP 400 按内容拒）记 `failedBatches`，这几对不算进比例的分母；每一批的报错记在报告的 `failures` 里、命令行也印出来。断线、限流、欠费、没配密钥时整条命令停下，退出码 2，已经核完的篇照常打印。
- 花钱。平均一篇 Stratechery 约 65 段、1.9 万英文字符，送进去约 1.2 万输入 token；输出主要是思考 token，事先算不准。先跑几十篇，看最后一行的用量再决定扩不扩大。不要接进启动、部署或夜间任务。

## content_hash 与待译队列

`article_translations.content_hash` 必须等于 `articles.content_hash` 且 `complete`，这篇才算译完。`content_hash()` 把 `published_at` 固定按 Asia/Shanghai 打戳；若按 UTC `isoformat()` 重算会对不上，待译队列会把已译篇反复拿出来（`--limit 2` 时整队像卡住）。

时区漂移或改过日期后，跑：

```bash
PYTHONPATH=src python scripts/repair_content_hash_tz.py          # dry-run
PYTHONPATH=src python scripts/repair_content_hash_tz.py --apply
```

对齐拒绝会写入 `translation_attempts`（原文 hash 和检查版本）。同一 hash、同一版本下，12 小时内不再送模型；满 2 次后一直停，直到原文变了或 `ALIGNMENT_VERSION` 加一。请求失败只把间隔从 15 分钟拉到 12 小时，不设永久次数。本进程里失败过的 id 仍会先跳过。点名 `--article-id` 不受这条队列限制。数字没对上不再算对齐拒绝，见下面「数字核对」。有段先放英文、已经入库但没译完的，也记一次（`rejected`，原因 `untranslated:` 加上那几段的问题；断线时 `failed` / `request-failed`），不记的话待译队列马上又把它拿回来。所以同一版本下这样的一篇自动再补一次，还补不上就停，要点名。

## 数字核对：对不上记待核，整篇照样入库（2026-11-07）

以前每段译文的数字都要按 `numbers.py` 的规则和原文对上，任何一段对不上，这篇已经译好的批次全部丢掉，记一次对齐拒绝，同一篇拒两次就停。中文写数字的方式没有边：20世纪90年代、「在20个国家有1000名员工」（地点挪到前面）、五五分成、全天候（24/7）。规则补了五轮（#245 到 #249），#245 之后通过率约 15%，版本 6 实跑 9 篇只过 1 篇（5 篇数字拒收，3 篇 SSL 断线）。一篇长文几十处数字，每处都要过，整篇通过的概率按处数连乘往下掉。Zhilin 11-07 选了「记下待核，照样入库」。

现在（`ALIGNMENT_VERSION` 7 起；8 是上面按句切开不丢链接那一条）：

| 情况 | 处理 |
| --- | --- |
| 一段的数字按规则没对上 | 同一批里这几段合成一次请求再译，`repair` 里列出原文数字。重译对上了就换上；还没对上、重译把链接弄坏或者请求失败，留原来那份 |
| 补译后仍没对上 | 照样写入。回执 `provenance.number_review` 记下这些段的序号（ordinal），`research-translate` 打印 `number_review=N` |
| 某段的数字正好是同一批另一段原文的 | 串段。这次回答整批不信，对半拆开重问；一直串的那一段单独重译两次，还不行先放英文（版本 9，见下一节；7、8 是整篇不入库） |
| 链接、图片、代码、占位符不对 | 只重译这一段，最多两次，还不行先放英文（版本 9；7、8 是整批再译一次再不行整篇不入库） |
| 条数不对、id 或 `source_hash` 没逐项回显 | 先按原批重来一次，再对半拆开，直到一段一批；一段一批还不对，这一段先放英文 |
| 标题的数字没对上 | 再要一次；两次都没对上，用第一次的 |

`number_review` 是写入时按当时的规则算的。`verify` 不比较它：`numbers.py` 以后再改，已入库的回执不会变成不兼容。`verify`（文章页每次打开都走）也不重核数字，只重签逐段的原文、译文和外壳。`research-bilingual-qa` 按现在的规则重算，列成告警 `numbers-unverified`（WARN，不算 FAIL）。

对照页：有回执（`mapped`）的译文不再按字面数字的位置猜错位。中文常把「in 2015」挪到「增长10%」前面，以前一段语序调整就让整页以「段落数字锚点不一致」退成两栏。没有回执的旧稿仍按这条把关。

查哪些译文有待核的段（只读）：

```sql
SELECT t.article_id, jsonb_array_length(t.provenance->'number_review') AS n
FROM article_translations t
WHERE jsonb_array_length(coalesce(t.provenance->'number_review', '[]'::jsonb)) > 0
ORDER BY n DESC, t.article_id;
```

`numbers.py` 的规则现在只决定哪些段进待核、补译要不要换上，和整篇能不能入库无关。补规则能让待核少一些，不必再为一篇文章能不能入库去补。

## 一段出错不连累整篇（2026-11-07，`ALIGNMENT_VERSION` 9）

以前译制失败的单位是整篇：一段的链接占位符没还原、一段的数字串到了别的段、一段一批时模型仍少回或者 id 没回显、写回后一段多切出叶子，这篇已经译好、付过钱的批次全部丢掉，记一次对齐拒绝，同一版本拒两次就再也不排队。断线、限流时也一样，前面译好的批次不入库。一篇长文几百段，每段都要一次过，整篇通过的概率按段数连乘往下掉；补一条规则只救得了一类段，下一类照样整篇作废。Zhilin 11-07 要「彻底修好、不靠一条条死规则」。

现在失败的单位是段。下面几种都只处理出问题的那一段，别的段照常入库：

| 这一段的情况 | 处理 | 记下的原因 |
| --- | --- | --- |
| 译文空白；链接、图片、代码、占位符还原不了或对不上；写回后会多切出叶子 | 这一段单独再译，最多两次（`_SLOT_RETRIES`），提示里说上一次哪里不对（`_SLOT_NOTES`）。还不行先放英文 | `empty`、`unshield`、`links`、`media`、`code`、`placeholder`、`shape` |
| 同一批的回答里有一段写的是别的段的数字 | 这次回答整批不信（段和段可能整体错开），对半拆开重问，直到找到那一段；它单独再译两次，还串就先放英文。「别的段的数字」要是那一段才有、这一段原文里没有的数，见下面「串段怎么判」 | `numbers-misplaced` |
| 交回的还是英文（2026-11-11）：原文是成句的英文，译文里英文字母还有原文一半以上、汉字不到原文字母数的 5% | 和串段一样整批不信，对半拆开重问；拆到一段一批还是英文，单独再译两次，还不行先放英文。见下面「串段：交回英文、两段中文一样」 | `english` |

| 条数不对、id 或 `source_hash` 没逐项回显、回答不是 JSON、这一批被接口拒（HTTP 400、413、422） | 原批重来一次，再对半拆开，直到一段一批；一段一批也重来过还不行，先放英文 | `response-*`、`http-400` 这类 |
| 整篇写回后叶子数或外壳对不上（单看一段判断不了的，比如定义列表的打包） | 二分找出是哪几段，这几段先放英文，别的段照常签回执 | `receipt-shape` |
| 数字按规则没对上 | 不变：同一批补译一次，仍不行照样写入，记进 `number_review` | |
| 断线、超时、限流（429）、欠费（402）、5xx | 服务那头的事，换哪一段问都一样：后面的批和标题不再问，已经译好的段先存下，按请求失败记冷却。Grok 要重新登录时照旧直接退出（退出码 2），这一篇这次不入库。`partial … (request-failed)` 后面接着印那一次的报错（版本 10 起），分得清是断线、超时、限流还是欠费，断线时还写着同一请求试了几次、各连了几秒。点名补译的，除了欠费和鉴权，这一轮最后隔 2、10 分钟各自动再补一轮（见上面「译制」一节） | `request-failed` |

先放英文的段，序号（ordinal）记进回执 `provenance.untranslated`。回执照样逐段签名，英文那几段的 `target` 就是原文，`verify` 照样是 `mapped`；对照页照常逐段对照，那几段只有英文，正文上方一句「部分段落没有译文。」。这一篇 `complete` 为假，记一次 `translation_attempts`（`rejected`，原因 `untranslated:` 加上上表的原因，几种用逗号隔开；只缺标题时是 `untranslated:title-empty`），12 小时后再进待译队列。`research-translate` 打印 `#123 partial segments=… untranslated=N (links,shape)`，`research-bilingual-qa` 报 WARN `untranslated`。一段都没译出来时整篇不入库，错误交给 CLI 记冷却，和以前一样。

下次译制只补没译出来的段。原文没变的段按原文身份复用已有回执里的译文，不再送模型：身份由 `provenance.py` 的 `reuse_key` 算，是整段 HTML（字、链接、图片、代码、标签）的摘要，只是不看 `data-src-para` 编号，前面多切或少切一段，后面的段仍认得出来。只复用这一版 `PIPELINE`（清洗、切段）签的回执里、自己的校验值对得上、链接图片和原文一致的段；没译出来的段和没有回执的旧稿不复用，整篇照常译。上一份回执不是现在这一版提示词译的（回执的 `prompt_versions` 不是只有 `PROMPT_VERSION`），也不直接复用，整篇按现在的提示词重译，见「提示词」。原文改了一段，只重译那一段。标题在原文 hash 没变时也复用。复用完和库里一字不差、回执也一样就不写库，检索块也不重切（打印 `(unchanged)`）；译文没变但回执变了（清洗规则改过、原文指纹变了）照样写，重签回执。

要换掉已经签过回执的译文（换了模型、提示词，或者觉得译得不好）加 `--fresh`：整篇重译，哪段重译失败就退回已有的那段译文，不会变成英文；一段新的都没译成时不写库，库里那份原样留着。

按句、按 `<br>` 行、定义列表切开，都只在切开再拼回去不丢字、链接、图片和代码时才切（见「段对齐」）。以前会丢东西的段让整篇过不了 `materialize`，现在整段当一个叶子。

### 串段怎么判（2026-11-08，`ALIGNMENT_VERSION` 10）

一段的数字按规则没对上，只说明规则没认出这种写法（`the next day` 写成「第二天」、`a thousand` 写成「一千」），或者真漏了数，这种记待核。串段是另一回事：模型把别的段的内容写到了这一段的位置上，证据是译文里出现了**那一段才有、这一段原文里没有的数**。所以 `misplaced_slot` 只拿「有这一段原文没有的硬数字」的邻段来比，译文和它的数字对上才算串段。

版本 9 只看译文和邻段的数字对不对得上，两种正常译文被当成了串段，11-07 重译 23 篇时各有一段先放了英文：

- 22254：问句「Yeah, January 2007.」和回答都写着 January 2007，回答里还有 the next day。回答译成「2007年1月……第二天……」，规则认不出「第二天」，又和问句的数字对上了。
- 22183：一段写 a thousand percent 和 Formula 1，译文写「一千」「一级方程式」，一个阿拉伯数字都没有；邻段唯一的数夹在 F1 里，也算「没有数字」，两边就「对上」了。

拿线上 22 篇对照页验过：两种都不再判串段；把同一批里别的段的译文换进来造了 6884 个真串段，版本 9 抓到 5505 个，版本 10 抓到 5436 个，少抓的 69 个里 56 个是换进来的译文里没有一个数是这一段原文没有的，单凭数字本来就分不出，只能交给待核和漏句抽查。

### 串段：交回英文、两段中文一样（2026-11-11、11-13）

串段是一段的中文写进了别的段。按数字认的见上一节；没有数字时，下面两种迹象也认。

#### 交回英文的段

11-11 全部译完后抽查发现：模型偶尔把相邻两段当成一段，前一段的位置写了两段的中文，后一段原样交回英文。以前的核对都放行了：空白、链接、占位符、结构都没毛病，英文自己的数字当然和原文对得上，没有数字时串段也判不出来。页面照样逐段对照，只是那一对只有英文，上一对的中文多一段话；「只看中文」里两段的中文后面跟着后一段的英文。意思没丢，读着别扭。11-11 晚上把线上 2409 篇 Stratechery 对照页扫了一遍（只读）：全部逐段对照，18 篇各有一对只有成句的英文，里面有几篇是没译完、本来就记在 `untranslated` 里的段，准数看盘点。例：22618 华尔街日报引文的第二段，21218 引的克里斯坦森那两段的第二段。

`provenance.untranslated_english` 认这种段：原文是成句的英文（至少 12 个英文词，其中至少 3 个小写虚词，the、of、which 这类），译文里英文字母还有原文的一半以上、汉字不到原文字母数的 5%。人名列表、书名、短标题凑不够虚词，照原样留着不算；只把「MA：」换成「马克：」、后面整段照抄英文的算；译得太短（漏内容）不归它管。拿线上 26 篇对照页（1500 多对）试过：上面那几处全认出，人名列表、书名、短标题和别的只有英文的对一个没误判。

怎么处理：

- 译制时：一段交回英文记成 `english`（`_accept`）。同一批里有一段这样，和串段一样整批不信、对半拆开重问：旁边那段看着没毛病，其实多写了一段话，单独重译交回英文的那一段，中文会写两遍。拆到一段一批还是英文，带着提示单独再译两次，还不行先放英文、记进 `untranslated`。补译数字时交回英文也不收（英文的数字当然对得上）。
- 复用已有回执时：交回英文的段和前后各一段都不复用（`reusable_targets`），再译时这三段一起重译。
- 已经入库的：盘点渲染页面时顺带数（`echoed_slots`），记进清单里的 `misplaced`，见下面。

#### 英文不同、中文一样的两段

11-11 晚另一个线程抽查时看到 21938 引的 Andreessen 那几句（三句各成一段的短句和后面一段）：第一句的中文没了，后两句各拿了下一段的中文，后面那段对上了，于是它和前一句的中文一字不差。这几段在同一批里（本地按原文切段核过），id、`source_hash` 都回显对了，内容整体错开一格。没有数字，也没有交回英文，以前的核对都看不出来，只剩「英文不同、中文一样」这个迹象。

`provenance.copied_targets` 认这种段：相隔不到 `COPY_SPAN`（12，一次请求最多送的段数）段的两段，去掉标签、标点和空白、不分大小写比，英文不同、中文一字不差。中文不到 8 个汉字的（「是的。」「对。」这类本来就常一样）不算；一段英文包含另一段的不算：同一段话又引一遍、前面多了说话人，目录里的小标题和正文里只差大小写、连字符的同一个小标题。11-13 拿 11-11 晚扫的线上全部对照页（2454 篇，只读）验过：整对中文一样、英文不同的 17 处里，规则认出 5 篇各一处（21938、21120、22204、22223、22776），都是真错开（一段的中文没了，或者两段写成同一段的中文）；没认的 12 处是短回答、只差大小写的小标题和隔得远的同一个词，都是本来就该一样的。

- 译制时：同一批里有这样的两段，和串段一样整批不信、对半拆开重问，拆开以后各自收下。只比同一次回答里的段：错开只会发生在一次回答里。
- 复用已有回执时：这两段前后各 `COPY_SPAN - 1` 段都不复用（`reusable_targets`）。从哪一段开始错开看不出来，一次回答最多这么多段，这一片一起重译。相邻都只数要译的段，原文就是中文、不用译的段不算。
- 已经入库的：盘点渲染页面时顺带数（`copied_slots`），记进清单里的 `misplaced`。

#### 盘点和补译

盘点摘要里一行「串段（一段的中文写进了别的段）N 篇：交回英文的段 a 段，相近两段英文不同、中文一字不差的 b 段」，清单里这些篇记在 `misplaced`。`research-translate --from-inventory misplaced --workers 4` 只补这几处附近的段，别的段照旧复用；补完再盘点，这一行应是 0 篇。没动 `ALIGNMENT_VERSION`：这是收紧，以前拒掉的篇不会因此能过，用不着重新排队。

还认不出的：一段的中文里多带了邻段的一两句、邻段自己的中文也在（没丢内容，只是同一句中文在相邻两对里各出现一次）。11-11 晚的页面扫描里约 56 篇有疑似，页面上分不清哪些是作者自己引了两遍，没做规则。

查哪些译文还有先放英文的段（只读）：

```sql
SELECT t.article_id, jsonb_array_length(t.provenance->'untranslated') AS n, t.complete
FROM article_translations t
WHERE jsonb_array_length(coalesce(t.provenance->'untranslated', '[]'::jsonb)) > 0
ORDER BY n DESC, t.article_id;
```

按原因看（只读）。同一类原因占了大多数时，去查提示词或那一类段的结构，不要为某一篇补规则：

```sql
SELECT reason, count(*) FROM translation_attempts
WHERE alignment_version >= 9 GROUP BY 1 ORDER BY 2 DESC;
```

没译出来那几段的英文也进了这篇的中文检索块（`article_chunks.lang = 'zh'`），只是这几段，补译写回后重切。

## 2026-11-02：来源回执与旧稿核验

当前修复及操作交接见 [双语映射说明](bilingual-mapping-2026-11-02.md)。上面的历史 PASS／段数记录是当时作者核对的结果，不代表当前旧库已经通过逐段语义验收。新稿须带有序源段身份和持久回执，资源按槽核对；数字也按槽核对，对不上的记进 `number_review`（见上面「数字核对」）。不再用近重复复用覆盖译文，也不删段凑数量。

没有回执的旧稿明确标记未核验，QA 至少 WARN；不兼容则保留完整原文和译文并 FAIL。可以无损按唯一有序事实锚点展开的旧粗段会细分展示，仍需人工核对。有序投影通过之后，展示层会再隐藏长英文的重复、整句包含和近前缀：留下的那一对仍要有这些文字、数字、链接和结构，锚点改挂过去；中文各自带独有说法的不隐藏。这一步不改库，也不把整页退回两列。

新 `research-bilingual-audit --dry-run` 始终只读，可输出不含正文的定向计划；没有 apply、模型请求、启动维护或自动历史回填。`research-translate --recheck --dry-run` 也改为只读。CLI 同一进程内失败篇在 loop 睡醒后仍跳过，失败退出码为 1。重启进程也不会立刻重试：对齐拒绝看 `translation_attempts` 的冷却和次数，原文 hash 或检查版本变了才重新排队。
