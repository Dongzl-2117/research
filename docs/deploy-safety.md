## 后续自动部署

- fetch 后立即固定 `FETCH_HEAD^{commit}`，仅从该对象 `git archive` 构建；配置和 compose 文件也来自快照。不会 merge、reset、clean 或把本机未推送提交、未跟踪文件打入镜像。运行中的配置留在 `data/releases/<SHA>/config`，不依赖临时构建目录。
- CI 必须是该 SHA、名称为 Tests、来自 GitHub Actions 的最新匹配检查，且结论为 success。旧的成功不能覆盖新的失败。`FORCE=1` 只重试达到次数上限的失败部署，不绕过 CI、任务锁、协议或迁移检查。
- 宿主机用 Python 标准库 `fcntl.flock`：六个定时脚本持共享锁，部署持独占锁。锁文件不删除；没有 PID 重用/删锁竞争，也没有检查后再启动任务的空档。Python 3 标准库适配 macOS，shell 入口仍兼容 bash 3.2。需要的辅助 `.py` 文件要随脚本一起安装。
- 数据库用固定 advisory session lock。CLI 的 `prepare` 连接及网页后台摘要/观点/论点/问库任务持共享锁，翻译服务每篇文章持共享锁，覆盖 #72 HTTP worker 与开发排障 CLI，内部 commit 不释放；开发 CLI loop 在空队列休眠前关闭连接，HTTP worker 的空闲连接不持任务锁。部署竞争记为 deferred，不算模型失败。部署在独立的一次性容器持独占锁，`up app` 不会替换这个锁容器；旧任务没完成就留待下一轮，新任务拿不到共享锁就延后。新 app 启动不需要维护锁，也不会写数据。
- 先构建和做只读迁移校验，再仅 `up -d --no-deps --no-build app`；不更新数据库容器。健康检查同时验证数据库可用和返回的构建 SHA，不能拿旧进程的 200 响应当成功。
- 健康失败时，在独占锁仍持有的窗口内尝试用记录的旧镜像 ID、旧配置和旧 SHA 重建 app，再检查旧版本健康；状态明确记失败。旧版本不健康时需要人工处理。代码回退不等于数据库恢复，脚本不会 `pg_restore`、删卷、删正式数据或自动执行迁移。
- 数据库迁移集合必须与镜像相等，因此有新迁移、旧迁移缺失或数据库比镜像新时默认阻断。即使迁移可重复执行，也不能当成可逆；独立维护提交的数据变更无法靠换回镜像撤销。
- 成功发布保存 `data/releases/<SHA>/docker-compose.yml` 和 `release.json`。mini 上后续人工复建必须使用这两个文件及原项目目录，带 `--no-build --no-deps app`；不要直接用脏工作树的 `compose up --build`。不要删除仍被运行中或回退镜像使用的配置目录和镜像。镜像/配置保留与清理由维护者单独安排，本脚本不自动删除。

## 数据、检索与浏览边界

- `owner_ids` 是账户身份，`poster_names` 只作显示名。相同昵称的别的账户是 guest；已登记账户改昵称仍是 owner。方伟的登记取自 #56 已公开记录的 `group.owner.user_id` 证据；本次未访问原始归档重新核验。首次交接仍需维护者与 mini 的 group/topic 原始响应核对，不能从昵称反推 ID。
- 缺账户 ID、或来源没有登记账户（乘风破浪）记 unknown。旧帖正文继续在来源时间线、阅读页、检索可见，页面明确写「账户未核实」；不伪造可信账户，也不隐藏整个来源。未知身份不新增星主观点；角色重算不删除既有观点，已核实为其他账户的观点被读取条件过滤。已有缓存和未知身份的完整归属整理仍需定向人工核查，不以全库付费重写解决。
- ANN 近邻、范围内穷举和关键词候选的向量补分都核对模型、当前块存在和标题/章节/正文 hash。回填在请求前后复核块；本轮拒绝的键加入 skip，整批被拒也能处理后面的块。保留 HNSW 先召回再过滤的路径；不改变检索基线和阈值。并发重切块后旧向量即使暂存，也因 hash 不匹配不能参与新正文排序。
- 公司页 GET 仅显示已有观点/论点/摘要及缺口，不调用排队、模型，也不同步来源表。旧的 `RESEARCH_THESES_AUTO=1` 不再允许公司页 GET 生成。生成继续使用有数量/时间上限的 CLI 和夜间任务；其他页面既有摘要生成入口此次未整体改造。
- 引用定位要求全部规范化文字连续接上，不能以相同的长开头认证虚构尾句；完整 `comments` 优先于预览（含完整空列表）；纯文本只去成对的强调标记，保留乘号、填空、变量下划线和行内代码符号。Claude 的提示框修复继续保留。
